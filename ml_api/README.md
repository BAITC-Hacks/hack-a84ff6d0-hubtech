# ML API: месячный прогноз для IEK и Systeme Electric

Это отдельный сервис для вызова уже обученных моделей по HTTP. Он возвращает
**прогноз продаж за полный месяц в единице товара**, а не фактические продажи. Модели
обучены на зарегистрированных продажах из месячных отчётов. Количество
закупки, страховой запас и текущий остаток здесь не рассчитываются.

Сервис использует выбранные модели последнего эксперимента с декомпозицией:

- `models/iek/decomposition_experiment/selected_model.pkl`;
- `models/systeme/decomposition_experiment/selected_model.pkl`.

Выбранный вариант может быть бустингом, средним или декомпозицией. Название папки
не означает, что для каждого поставщика обязательно выбрана декомпозиция.
Более ранние `models/<поставщик>/selected_model.pkl` не используются как замена.

## 1. Подготовить окружение

Команды ниже выполняются **из корня репозитория**, нужен Python 3.11 или новее.
Если `.venv-ml` уже создано, повторно создавать его не нужно.

```bash
python3 -m venv .venv-ml
.venv-ml/bin/python -m pip install -r ml_api/requirements.txt
```

Файл `ml_api/requirements.txt` уже включает библиотеки подготовки и обучения.

## 2. Подготовить модели до запуска сервиса

Если согласованные результаты подготовки и обучения уже есть, переходите к
запуску сервиса. Для воспроизведения на предоставленных выгрузках:

```bash
# Подготовка и базовое сравнение IEK
.venv-ml/bin/python scripts/prepare_ml_data.py --as-of 2026-09-23
.venv-ml/bin/python scripts/train_iek_model.py

# Подготовка и базовое сравнение Systeme Electric
.venv-ml/bin/python scripts/prepare_systeme_data.py --as-of 2026-09-23
.venv-ml/bin/python scripts/train_systeme_model.py

# Декомпозиция и выбор итогового варианта для каждого поставщика
.venv-ml/bin/python scripts/run_demand_decomposition.py --supplier all
```

Базовое сравнение нужно для последнего шага: декомпозиция сравнивается с ранее
обученными вариантами. Методика описана в [DECOMPOSITION.md](../scripts/DECOMPOSITION.md).

Для каждого поставщика сервису нужны согласованные результаты одного запуска:

| Артефакт | Назначение |
|---|---|
| `models/<поставщик>/decomposition_experiment/selected_model.pkl` | Выбранная модель |
| `data/ml/<поставщик>/prediction_features.csv` | Признаки прогнозируемого месяца |
| `data/ml/<поставщик>/monthly_panel.csv` | Подготовленная месячная история |
| `data/ml/<поставщик>/preparation_report.json` | Правила подготовки, дата, месяц прогноза и минимальная история |
| `data/forecasts/<поставщик>/decomposition/report.json` | Метаданные эксперимента и контрольные суммы |
| `data/forecasts/<поставщик>/decomposition/selected_forecast.csv` | Контрольный прогноз выбранной модели |

В путях `<поставщик>` — `iek` или `systeme`, а в HTTP-запросе — `IEK` или `SYSTEME`.
Не редактируйте машинные CSV вручную и не смешивайте модель и признаки разных
запусков. Для нового периода нужны обновлённые источники и повторная подготовка;
простая смена даты не делает старые выгрузки актуальными.

При старте сервис:

1. Проверяет SHA-256 **двух используемых CSV**: `prediction_features.csv` и
   `monthly_panel.csv`, по отчёту эксперимента. Для работы API исходные Excel,
   транзакции и обучающая выборка не нужны.
2. Сверяет поставщика, выбранный алгоритм, даты и границу обучения между моделью
   и отчётами; для декомпозиции также сверяет силу тренда `damping`.
3. Проверяет ключи товаров, месяцы, схему и согласованность признаков с панелью.
   Для обычных моделей нужна та же версия scikit-learn, что была при обучении.
4. Рассчитывает прогноз всего каталога и сверяет доступные результаты с
   `selected_forecast.csv`. Согласованный снимок сохраняется в памяти.

Минимальная длина истории берётся из отчёта подготовки. Для декомпозиции
используется максимум этого порога и порога сохранённой модели. Недостаточная
история даёт статус `insufficient_history`, а не выдуманный нулевой спрос.

## 3. Запустить сервис

```bash
.venv-ml/bin/uvicorn ml_api.app:app --host 127.0.0.1 --port 8020
```

Оставьте этот процесс работающим. Запросы из следующих примеров выполняйте во
втором терминале или из приложения, которому нужен прогноз.

- Адрес: `http://127.0.0.1:8020`.
- Интерактивная документация Swagger: [http://127.0.0.1:8020/docs](http://127.0.0.1:8020/docs).
- Точный контракт полей и типов: [OpenAPI](http://127.0.0.1:8020/openapi.json).
- Экспорт схемы в репозитории: [openapi.json](openapi.json).

Схему можно обновить без загрузки моделей: `.venv-ml/bin/python -m ml_api.export_openapi`.

HTTP-запросы выбирают готовые результаты **из памяти**: не обучают модели,
не читают файлы и не пересчитывают прогноз для каждого обращения.
После пересборки артефактов перезапустите процесс, чтобы загрузить новую версию.
Чтобы остановить его, нажмите `Ctrl+C` в терминале сервиса.

По умолчанию API доступен только локально; для вызова сервером backend браузерный
CORS не нужен. Если сервисы находятся в разных контейнерах или на разных машинах,
у каждого свой `localhost` — настройте доступный им частный адрес сервиса.

## 4. Проверить готовность

```bash
curl -sS http://127.0.0.1:8020/health
curl -sS http://127.0.0.1:8020/v1/models
```

`GET /health` показывает состояние `ok` или `degraded` и доступность моделей.
`degraded` означает, что не все модели доступны: сам процесс при этом может
работать. `GET /v1/models` возвращает метаданные актуальных выбранных моделей.
Перед запросом прогноза проверяйте доступность нужного поставщика и поддерживаемый
месяц, а не только факт запуска процесса.

## 5. Запросить прогноз через curl

```bash
curl -sS -i http://127.0.0.1:8020/v1/forecast \
  -H 'Content-Type: application/json' \
  -d '{
    "supplier_id": "IEK",
    "forecast_month": "2026-09-01",
    "skus": ["010300001_"]
  }'
```

| Поле запроса | Что передать |
|---|---|
| `supplier_id` | Строго `IEK` или `SYSTEME` |
| `forecast_month` | Первый день поддерживаемого прогнозного месяца, `YYYY-MM-01` |
| `skus` | От 1 до 500 уникальных кодов 1С строками, каждый длиной 1–128 символов |

Код передавайте целиком, включая ведущие нули и `_`. Для Systeme замените
поставщика на `SYSTEME` и используйте его коды. Артикул поставщика и название
товара не заменяют код `sku`. Пробелы по краям кода удаляются до проверки
уникальности; числовые коды и лишние поля запроса не принимаются.

В текущих артефактах прогноз относится к **полному сентябрю 2026**, по истории до
августа. Дата снимка `2026-09-23` не превращает результат в прогноз оставшихся
дней сентября. Произвольный другой месяц запросить нельзя: сервис вернёт `422`.

## 6. Как читать результат

Общие поля ответа:

| Поле | Значение |
|---|---|
| `supplier_id` | Поставщик |
| `model` | Выбранный алгоритм |
| `model_version` | Непрозрачный хеш шести артефактов снимка; не время HTTP-запроса |
| `data_as_of` | Дата снимка данных |
| `forecast_month` | Месяц прогноза |
| `trained_before` | Исключительная граница обучения: использована история строго раньше этой даты |
| `forecast_scope` | Всегда `full_month`: прогноз полного месяца |
| `warnings` | Ограничения и предупреждения |
| `items` | Результаты по запрошенным товарам |

Для каждого товара возвращаются `sku`, `predicted_qty`, `unit`, `status` и
`history_observed_months`. Интерпретация `status`:

| Статус | Значение |
|---|---|
| `forecast` | Прогноз рассчитан; количество дано в `unit` |
| `insufficient_history` | Недостаточно известной истории; `predicted_qty = null` |
| `unknown_sku` | Код не найден у поставщика; `predicted_qty = null`, `unit = null` |

У неизвестного кода `history_observed_months` тоже равно `null`. Для известного
товара это число известных неотрицательных месяцев до `forecast_month`.

`null` означает отсутствие оценки. Не заменяйте его нулём: нулевой прогноз
означал бы, что модель ожидает нулевые продажи. Не складывайте количества с
разными единицами измерения.

`explanation` содержит компоненты только тогда, когда выбранная модель —
декомпозиция. Для бустинга и остальных вариантов поле равно `null`.
В декомпозиции применённый `trend_per_month` уже учитывает `damping`;
повторно умножать наклон на этот коэффициент не нужно.
Наличие прогноза не означает, что он уже учитывает недополученный спрос при
отсутствии товара или что можно автоматически размещать заказ.

Проверенные результаты текущего снимка для полного сентября 2026
(`trained_before = 2026-09-01`, `data_as_of = 2026-09-23`):

| Поставщик | SKU | Выбранная модель | Прогноз | Известных месяцев |
|---|---|---|---:|---:|
| IEK | `010300001_` | `boosting_squared` | 10.109377101567565 шт. | 26 |
| SYSTEME | `010400432_` | `decomposition` | 3.5654025642190508 шт. | 32 |

Фрагмент `items` для первого примера:

```json
[
  {
    "sku": "010300001_",
    "unit": "шт",
    "status": "forecast",
    "predicted_qty": 10.109377101567565,
    "history_observed_months": 26,
    "explanation": null
  }
]
```

После переобучения числа и `model_version` могут измениться. Дробный прогноз
в штуках допустим: это ожидаемый объём, а не уже округлённое количество заказа.

## 7. Пример клиента на Python

Установите клиентскую библиотеку в окружении приложения, которое вызывает API:

```bash
python -m pip install httpx
```

```python
import httpx

request = {
    "supplier_id": "IEK",
    "forecast_month": "2026-09-01",
    "skus": ["010300001_"],
}

with httpx.Client(base_url="http://127.0.0.1:8020", timeout=30.0) as client:
    response = client.post("/v1/forecast", json=request)
    if response.status_code != 200:
        print("Ошибка API:", response.status_code, response.text)
    response.raise_for_status()
    result = response.json()

print("Модель:", result["model"], "версия:", result["model_version"])
print("Месяц:", result["forecast_month"])
print("Предупреждения:", result["warnings"])

for item in result["items"]:
    if item["status"] == "forecast":
        print(item["sku"], item["predicted_qty"], item["unit"])
    else:
        print(item["sku"], "прогноз недоступен:", item["status"])
```

## 8. Типичные ответы и действия

| Результат | Что проверить |
|---|---|
| `200` | Проверить `status` каждого товара и общие `warnings` |
| `422` | Формат запроса, поставщика, поддерживаемый месяц, уникальность и число кодов |
| `503` | Модель или связанные артефакты недоступны/не согласованы; проверить `/health`, пересобрать нужный набор и перезапустить сервис |
| Ошибка соединения | Запущен ли сервис на `127.0.0.1:8020` |

Неизвестный SKU обрабатывается внутри `items`, а не как нулевой прогноз или сбой
всего запроса. Если пример и работающий сервис когда-либо разойдутся, используйте
актуальную схему `/openapi.json` как точное описание контракта.

## Подключение к существующему backend

Подключение реализовано в `backend/app/core/ml_client.py` и
`backend/app/core/recommend.py`. Существующий `POST /api/recommend` запрашивает
ML-прогнозы пакетами по 500 кодов у каждого поставщика. Frontend продолжает
обращаться к тому же backend-эндпоинту.

В `backend/.env` доступны настройки (эти значения используются по умолчанию):

```dotenv
ML_API_ENABLED=true
ML_API_URL=http://127.0.0.1:8020
ML_API_TIMEOUT=10
```

Интеграция применяется к `DATA_SOURCE=excel`. Синтетические данные и CSV
сохраняют прежний алгоритм. Для запуска нужны два процесса и отдельные
окружения: версии pandas/numpy backend и обучения отличаются.
Из корня проекта:

```bash
# Терминал 1: модели
.venv-ml/bin/uvicorn ml_api.app:app --host 127.0.0.1 --port 8020
```

```bash
# Терминал 2: backend (создать окружение, если его ещё нет)
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
backend/.venv/bin/uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8017
```

```bash
curl -sS http://127.0.0.1:8017/api/recommend \
  -H 'Content-Type: application/json' \
  -d '{"explain": false}'
```

У строк результата поле `rationale.forecast_source` равно `ml_api` или `legacy`.
Для ML также возвращаются `forecast_model`, `forecast_model_version`,
`forecast_month`, `forecast_monthly_qty`. В `data_quality.ml_api` находятся
счётчики использования и резервного расчёта до фильтрации строк без заказа.

**Пересчёт горизонта:** `avg_daily_demand = predicted_qty / days_in_month`,
затем существующий расчёт использует `avg_daily_demand × (lead_time + review)`.
Это приближение с постоянной суточной скоростью, в том числе после перехода
в следующий месяц. Это не отдельный ML-прогноз следующего месяца или проверенный
35/49-дневный прогноз. Предупреждение включено в каждую ML-строку.

Страховой запас остаётся эвристикой backend: для дневного sigma берётся максимум
его прежней оценки и `sqrt(avg_daily_demand)`. Это не ошибка ML-модели и не
подтверждение заданного уровня сервиса. MOQ, кратность, остатки, поставки и
сортировка продолжают обрабатываться backend. Месячный ML-прогноз повторно
не корректируется на сезонность, тренд, опт или stockout; в раскладке
дополнительные коэффициенты равны 1, исключённый объём и uplift равны 0.

При недоступности ML, неподходящей дате снимка, неизвестном коде, короткой
истории, разных единицах или нескольких складах одного SKU используется
`legacy` с явным предупреждением. `null` не превращается в нулевой спрос.
Нулевой числовой ML-прогноз применяется как нулевой. Дата снимка ML должна
совпадать с датой расчёта backend; при обновлении данных перезапускайте ML-сервис.

Проверить интеграцию:

```bash
PYTHONPATH=backend backend/.venv/bin/python -m unittest tests.test_ml_integration -v
```
