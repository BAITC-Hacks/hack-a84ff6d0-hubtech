# ЭКТ — расчёт заказов поставщикам

Ниже описаны фактический сервис и методология расчёта после интеграции
`baitc/frontend@5a0ace2` от 23.09.2026. Работают персональный вход, две роли
`admin/manager`, постоянные заказы, сохранённые решения и очередь с отдельным
worker. Полное задание на многопользовательскую платформу — [ТЗ](docs/ТЗ_платформы.md),
целевые экраны — [контракт интерфейса](docs/ИНТЕРФЕЙС_ПЛАТФОРМЫ.md).
Независимое согласование руководителем, пять ролей и управляемые партии импорта
остаются целевыми требованиями. Отметка строки менеджером не заменяет такое согласование.

Сервис рассчитывает рекомендованное пополнение склада по выгрузкам IEK и
Systeme Electric, показывает исходные числа и ограничения данных, позволяет
скорректировать количество, утвердить позиции и выгрузить заказ в Excel.
Исходный кейс: [relly-problem.md](./relly-problem.md).

## Запуск

Поддерживаемая среда: Python **3.12**, Node.js **22.19+ в ветке 22.x или 24.x**. Установка 1С
для чтения приложенных файлов не нужна. Прямого подключения к её базе и обратной
записи заказа нет; см. [интеграцию 1С](docs/ИНТЕГРАЦИЯ_1С.md).

Полная пошаговая инструкция с lock-зависимостями, `.env`, созданием первого
администратора, миграциями и тремя процессами — [README](README.md)
и [DEPLOY](docs/DEPLOY.md). Нужны **API, worker и frontend**; запуск одного API
не выполняет новые задания. Браузер и API используют один origin через `/api`.

Ключ OpenAI необязателен. По умолчанию расчёт работает без сети и LLM;
числовая раскладка и шаблонные обоснования доступны всегда. Внешние AI-обоснования
включаются отдельно и ограничены временем и числом запросов.

## Источники и настройки

По умолчанию используется `DATA_SOURCE=excel`. Импортёр читает шесть файлов из
`IEK/` и шесть из `Systeme electric/`: динамику продаж, месячные продажи,
месячные остатки, MOQ/кратность, товары в пути и сезонность.
Список ожидаемых имён находится в `backend/app/data/excel.py::SUPPLIER_FILES`.

`DATA_DIR=.` указывает на корень проекта. Относительные пути разрешаются от
корня проекта, независимо от рабочей директории процесса.
`backend/.env` также загружается по постоянному пути.

| Настройка | Значение по умолчанию / назначение |
|---|---|
| `DATA_SOURCE` | `excel`; также поддерживаются `synthetic` и `csv` |
| `DATA_DIR` | Корень с папками поставщиков; для контрольного CSV задайте `data/sample_csv` |
| `DATA_AS_OF` | Дата YYYY-MM-DD; Excel/CSV без неё берут день после последней продажи, synthetic фиксирован на 23.09.2026 |
| `IEK_LEAD_TIME_DAYS` | 21 день, допущение до подтверждения поставщиком |
| `SYSTEME_LEAD_TIME_DAYS` | 35 дней, допущение до подтверждения поставщиком |
| `SERVICE_LEVEL` | 0.95 |
| `REVIEW_PERIOD_DAYS` | 14 |
| `EKT_CATALOG_ENABLED` | Включение обогащения локальным публичным справочником |
| `EKT_CATALOG_PATH` | Путь к JSON; по умолчанию `data/ekt/catalog.json` |
| `APP_DB_PATH` | SQLite пользователей, сессий, заданий, заказов, решений и аудита; одинаковый путь у CLI, API и worker |
| `JOB_TIMEOUT_SECONDS` | 600; предел времени отдельного расчёта |

Для приложенных файлов дата расчёта — **23.09.2026**. Это дата моделирования по
зафиксированной выгрузке; импортёр не выдаёт старые данные за текущие.
Смена файла сбрасывает кэш по его пути, времени изменения и размеру.
Каждый потребитель получает отдельную копию набора данных.

CSV-режим ожидает `sales.csv`, `stock.csv`, `in_transit.csv`,
`suppliers.csv`, `sku_suppliers.csv`, `stockouts.csv`.
Необязательный `catalog.csv` задаёт описания и реальные единицы.
Готовый минимальный набор, схема и эталонные результаты — [sample CSV](data/sample_csv/README.md).
Синтетический режим имеет фиксированную дату и seed; повторный запуск воспроизводим.

## Отдельная подготовка данных для ML

Из ветки `baitc/alish` выборочно перенесены скрипты `scripts/clean_monthly_data.py`
и `scripts/prepare_ml_data.py`, проверки и инструкции. Коммит `5facda2` содержит
производные данные IEK; исходные шесть Excel совпадают с основной веткой.
Скрипты создают локальные таблицы очистки, признаки, временные train/validation/test
и отчёты качества. Они не используются текущим `generate_recommendations`.
`data/ml/iek/` не соответствует шести CSV оперативного адаптера; значения
`DATA_SOURCE=ml` нет. Обучение модели не выполнялось. Добавлен отдельный [backtest текущего прогноза](scripts/BACKTEST.md)
на исходных месячных Excel обоих поставщиков; эти ML-CSV не подменяют его входы.

Особое различие: в рабочем импорте пустые месячные продажи считаются нулями,
а подготовка ML по умолчанию сохраняет их неизвестными. Поэтому выборка исходной
ветки содержит только положительные цели. Политику нужно согласовать до
сравнения моделей; смешивать результаты двух режимов без этого нельзя.
Аудит коммита, численность, правила сверки и назначение файлов:
[АУДИТ_ВЕТКИ_ALISH.md](docs/АУДИТ_ВЕТКИ_ALISH.md).

## Товарный справочник ekt.kz

Каталог сайта загружается отдельным скриптом `backend/scripts/sync_ekt_catalog.py`
в `data/ekt/catalog.json`. Совпадение по точному строковому `sku` добавляет
товарную категорию, подкатегорию, характеристики и ссылку на карточку.
Внутренняя `category` и внешняя `product_category` остаются разными полями.
Нули и подчёркивания в кодах значимы; конфликты не объединяются автоматически.

Это обогащение не меняет количества, единицы, цены, MOQ/кратность и сроки.
Расчёт и экспорт не обращаются к сайту. Отдельный фильтр `product_category`
выбирает набор товаров, не меняя формулу отдельного SKU. Покрытие показывается
в `/api/meta` как `data_quality.catalog_enrichment`.

Контракт JSON, происхождение полей и обновление:
[КАТАЛОГ_EKT.md](docs/КАТАЛОГ_EKT.md). Для текущих параметров синхронизации
выполните из каталога `backend`:

```bash
./.venv/bin/python -m scripts.sync_ekt_catalog --help
```

## Нормализация и ограничения реальных данных

- Коды 1С сохраняются строками. Убираются лишние пробелы, переносы и табуляция.
  Даты транзакций приводятся к календарным дням.
- Отрицательные транзакции исключаются из регулярного положительного спроса
  как возвраты/корректировки. Месячные отчёты уже содержат чистые итоги:
  отрицательные итоги ограничиваются нулём, исходные значения остаются в `raw_qty`.
- Пустые месячные продажи трактуются как нули разреженного отчёта 1С.
  Пустые остатки остаются неизвестными. Это допущение видно в интерфейсе.
- Для Systeme Electric используется свободный остаток из датированного
  отчёта товаров в пути, где он есть. Иначе берётся последний известный
  начальный остаток месяца **с исходной датой и предупреждением**.
  Неизвестный остаток при расчёте принимается за 0 и требует сверки.
  Приходы и расходы между старым снимком и датой расчёта не восстанавливаются.
- Точных дневных интервалов отсутствия товара в этих файлах нет.
  Месячные остатки не превращаются в фиктивные stockout-периоды.
- Идентификаторов клиентов нет. Для крупных заказов используются строки
  транзакций и реальные номера документов. В CSV/синтетике поддерживаются
  реальные обезличенные client_id, если переданы.
- Категории Systeme перенесены из «Категория 2026». Категории без исходного
  значения помечаются как неизвестные, а не выводятся из названий.
- IEK «Мин. разр. к отгр.» используется как минимальное количество;
  Systeme «Кратность» — как кратность упаковки. Недоступные условия, включая
  сохранённые `#N/A`, заменяются операционным значением 1 с предупреждением.
- Коэффициенты сезонности поставщика применяются как приближение для
  отдельного артикула. Их влияние и происхождение показаны в обосновании.
- Формулы читаются по сохранённым значениям Excel. Внешние ссылки не
  открываются и не обновляются. Исходные файлы не изменяются.

Даты уже отгруженного товара берутся из заголовков приходов: у IEK именно
«поступление до», а не дата создания заказа. Это отдельные данные от
предположений о сроках новых заказов.

## Расчёт

Расчёт выполняется отдельно для каждой пары **артикул + склад**. При выборе
«Все» продажи, остатки и периоды отсутствия разных складов не смешиваются.
Список складов определяется данными; девять городов публичного сайта не создают
девять расчётных складов. Сейчас в транзакциях подтверждён только Алматы,
месячные отчёты и путь отнесены к нему с предупреждением.
Требования к расширению: [ГОРОДА_И_СКЛАДЫ.md](docs/ГОРОДА_И_СКЛАДЫ.md).

1. **Разовые крупные заказы.** Независимо проверяются документ + день
   и клиент + день внутри SKU/склада. Документы не отменяют клиентскую проверку.
   Для исключения нужны минимум пять положительных наблюдений на соответствующем
   уровне. Порог: выше `Q3 + 3 × IQR` и не меньше восьми медиан.
   Объединение найденных строк вычитается один раз; при совпадении детекций
   счётчик использует клиентское событие. Отсутствующий ID не объединяет
   анонимных покупателей, короткая история не признаётся доказательством опта.
2. **История спроса.** При наличии месячного отчёта его завершённые месяцы
   являются основным источником объёма. Транзакции используются для поиска
   крупных заказов; их объём вычитается только после сверки исходной суммы
   транзакций с итогом соответствующего месяца и не более этого итога.
   При расхождении источников месячный объём сохраняется, а строка получает
   предупреждение. Дневные наблюдения из месячных итогов не выдумываются.
   Текущий неполный месяц не сравнивается с полными месяцами.
3. **Stockout.** При дневной истории и явно переданных интервалах
   восстанавливается спрос соответствующего склада с учётом дня недели
   и месяца. Наблюдавшиеся продажи не уменьшаются, uplift равен разнице.
   В месячной ветке восстанавливается месячный объём после исключения опта.
   Частичный месяц оценивается по регулярным продажам на доступный календарный
   день; при согласованных транзакциях продажи внутри отсутствия вычитаются
   из оцениваемой потери. Без такой сверки предположение о продажах только
   на доступных днях явно показано в предупреждении. Полный месяц использует
   медиану до трёх предшествующих доступных месяцев, без будущих данных
   и каскадного использования восстановленных полных месяцев. Если опоры нет,
   компенсация не выдумывается. Пересечения интервалов считаются один раз.
   Дневные наблюдения из месячного итога не создаются; месячный остаток
   не заменяет явные интервалы. Формулы: [ML_И_ДАННЫЕ.md](docs/ML_И_ДАННЫЕ.md).
4. **Прогноз.** Сезонность нормируется к среднегодовому уровню, тренд
   оценивается по десезонализированным среднесуточным значениям с учётом
   реального расстояния между датами. Для дневной истории используются
   последние 90 дней для уровня и до 180 дней для тренда; для месячной —
   последние 3 и 6 месяцев соответственно.
5. **Горизонт.** Прогноз и учёт ожидаемых поставок используют один интервал:
   `[дата расчёта, дата расчёта + срок поставки + период проверки)`.
   Просроченные, недатированные и более поздние приходы не уменьшают заказ;
   исключённый объём показан отдельно.
6. **Потребность и партия.**

   ```text
   H = срок поставки + период проверки
   страховой запас = z(уровень сервиса) × σ × √H
   потребность = прогноз спроса(H) + страховой запас − остаток − учтённые приходы
   заказ = округление вверх max(положительная потребность, MOQ) до кратности
   ```

   Для месячных данных дневная вариативность неизвестна. Используется
   оценка по разбросу месячных среднесуточных значений и приближение Пуассона;
   это допущение отдельно указано.
7. **Срочность.** Проверяется покрытие до фактического дня поступления.
   Поздний приход не скрывает дефицит до этой даты. Если объёма в пути
   достаточно, но он опаздывает, строка показывает риск и нулевой
   дополнительный заказ с рекомендацией ускорить приход/переместить запас.

Результат — прозрачная оценка на доступных данных. [Временная оценка](scripts/BACKTEST.md)
выполнена для 3 017 SKU на завершённых месяцах: validation январь–июнь 2026,
test июль–август. Текущий метод не показал общего преимущества над предыдущим
месяцем. Метрики разделены по единицам и одинаковым парам SKU–месяц; оценка
прогноза продаж не доказывает эффективность всей закупочной политики.

## Корректировка, утверждение и экспорт

Интерфейс создаёт задание через `POST /api/recommend` с
`Prefer: respond-async` и ключом идемпотентности. Worker сохраняет исходный расчёт
в постоянном заказе; UI открывает его по `order_id`. Рабочий заказ и решения
не удаляются по прежнему TTL семидневного кэша снимков.

Менеджер видит свои заказы; администратор — все. Правки автоматически сохраняются
через `PUT /api/orders/{id}` с текущей `revision`. Интерфейс показывает состояние
сохранения; ошибка и конфликт не считаются успешной записью. При конфликте нужно
явно принять серверную версию или совместить правки. Незавершённый неверный ввод
остаётся локальным и блокирует экспорт.

Количество должно соответствовать MOQ/кратности; ноль исключает позицию.
Изменение количества снимает её утверждение. Положительную строку с неизвестной
единицей нельзя утвердить ни через UI, ни через API. Известные метры, штуки
и упаковки остаются раздельными в итогах.

Экспорт `POST /api/orders/{id}/export` получает только ожидаемую `revision`
и `approved_only`. Сервер берёт **сохранённые** решения и исходную рекомендацию;
нового прогноза нет. Несовпадение версии возвращает 409. Совместимый прежний
`/api/recommend/export` также не разрешает обойти сохранение новыми решениями.

- **Черновик Excel** содержит все положительные сохранённые количества и отметки.
- **Утверждённые** содержит положительные позиции с сохранённой отметкой менеджера.

Файл содержит лист заказа и лист параметров. Исходная рекомендация и количество
менеджера разделены; сохраняются код 1С, артикул поставщика, склад, единица,
ID расчёта, ID заказа, revision и владелец. Действие экспорта записывается в аудит.
Это табличная передача для сверки: загрузчик в целевую 1С и автоматическая отправка
поставщику не реализованы. История событий есть, полного архива каждой версии
решений и независимого согласования руководителем пока нет.

## Архитектура

- `backend/app/data/excel.py` — чтение, нормализация и аудит источников.
- `backend/app/core/recommend.py` — расчёт по артикулу/складу.
- `forecasting.py`, `outliers.py`, `stockout.py`, `replenishment.py` —
  прогноз, выбросы, восстановление спроса и потребность.
- `storage.py`, `repositories.py` — постоянные пользователи, заказы, решения, ревизии и аудит.
- `jobs.py`, `worker.py` — очередь, отдельный процесс расчёта, отмена и предел времени.
- `snapshots.py`, `export.py` — совместимость снимков и формирование XLSX.
- `backend/app/api/routes.py` — HTTP-контракты.
- `frontend/src/App.jsx`, `pages/`, `hooks/`, `orderUtils.js` — вход, история,
  расчёт, рабочий заказ, аккаунт и администрирование; на телефоне позиции представлены карточками.

## Проверки

Отдельные скрипты подготовки данных проверяются из корня:

```bash
backend/.venv/bin/python -m unittest discover -s scripts -p 'test_*.py' -v
```

Проверки работающего приложения:

```bash
cd backend
RUN_REAL_EXCEL_TESTS=1 ./.venv/bin/python -m unittest discover -s tests -v
./.venv/bin/python -m tests.validate_must_have

cd ../frontend
npm test
npm run lint
npm run build
```

Must-have-проверка использует данные с фиксированными датами и точными ожидаемыми
результатами: 14 проверок чувствительности источников, сезонность `70 → 140`,
линейный рост `203/день`, месячный stockout `40 → 70` с компенсацией `200`,
дневной stockout с тем же восстановленным объёмом, клиент с десятью документами
без двойного вычитания и два поставщика с обоснованиями. Категория проверяется
как фильтр, рост — как свойство истории. Внешний коэффициент роста не добавлен.
Это проверка поведения, а не точности на рабочих данных или официальный допуск.
Регрессионные тесты дополнительно проверяют импорт, даты/склады/партии и экспорт
с изменёнными количествами без повторного расчёта.


HTTP/worker и browser E2E выполняются отдельными сценариями в `qa/`.
Итоговые результаты, точная среда и границы подтверждения —
[приёмка](docs/ПРИЕМКА.md) и [отчёт по двум критериям](docs/ОТЧЁТ_ПО_КРИТЕРИЯМ.md).
