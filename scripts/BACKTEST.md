# Временная проверка месячного прогноза на реальных Excel

[`backtest_forecast.py`](backtest_forecast.py) измеряет ошибку существующей функции
[`forecast_monthly_demand`](../backend/app/core/forecasting.py), сравнивая её с двумя
простыми методами. Скрипт читает месячные продажи IEK и Systeme Electric, запускается
без сети и LLM, не обучает модель и не меняет рабочий алгоритм ради оценки.

## Запуск и результаты

Из корня репозитория, после установки зависимостей backend:

```bash
OPENAI_API_KEY='' backend/.venv/bin/python scripts/backtest_forecast.py
OPENAI_API_KEY='' backend/.venv/bin/python -m unittest discover -s scripts -p 'test_backtest_forecast.py' -v
```

На Windows используйте Python из соответствующего виртуального окружения; переменная
`OPENAI_API_KEY` скрипту не нужна и не читается. Рекомендуемый запуск использует
зависимости из [`backend/requirements.lock`](../backend/requirements.lock).

По умолчанию проверяются оба поставщика и обе политики пропусков. Дата фиксирована:
`--as-of 2026-09-23 --last-complete-month 2026-08`. Переход календарной даты сам по себе
не превращает сентябрь старого отчёта в полный месяц. Для новых источников границу
полноты нужно указывать явно, после проверки выгрузки. Это допущение о полноте, а не
подтверждение бухгалтерского закрытия месяца.

Результаты сохраняются в [`data/evaluation/`](../data/evaluation/):

| Файл | Содержимое |
|---|---|
| [`forecast_backtest.json`](../data/evaluation/forecast_backtest.json) | Протокол, периоды, версии библиотек, SHA-256 исходников и кода, количество SKU, покрытие, исключения и ограничения |
| [`forecast_metrics.csv`](../data/evaluation/forecast_metrics.csv) | MAE, WAPE, bias и размеры сравнимых групп, отдельно по поставщику, политике пропусков, периоду и единице измерения |
| `forecast_predictions.csv`, опционально | Каждая пара SKU/месяц: факт, три прогноза, длина истории, последний доступный месяц и статус исходной ячейки |

Для подробной проверки используйте `--write-predictions`; большой построчный CSV
по умолчанию не создаётся. `--output-dir` позволяет сохранить новый запуск отдельно
от зафиксированного отчёта. `--supplier IEK` / `--supplier SYSTEME` и `--scenario`
ограничивают запуск. Исходные Excel не изменяются. Источником единиц служат только
идентификационные столбцы месячных остатков; количества остатков в прогноз не попадают.

## Временной протокол

История в текущих матрицах начинается в январе 2024. Каждый прогноз делается на один
полный календарный месяц. В функцию передаются только известные значения месяцев
строго раньше целевого. Ещё одна проверка границы выполняется непосредственно перед
вызовом прогноза.

- **Validation:** январь–июнь 2026, шесть последовательных прогнозов.
- **Test:** июль–август 2026, два последовательных прогноза.
- Июльский факт может участвовать в августовском прогнозе после завершения июля.
  Это последовательная эксплуатационная проверка, а не прогноз двух месяцев из июня.
- Текущие Excel-коэффициенты сезонности не используются. Историческую сезонность
  функция оценивает сама, только из доступного прошлого.
- Текущие остатки, MOQ, путь, клиентские признаки и транзакции не используются.
- Скрипт ничего не подбирает по validation или test. Алгоритм и гиперпараметры не
  менялись для улучшения этих метрик. Предварительная разработка могла видеть сами
  исходные файлы: это не слепое перспективное испытание.

Validation выделен для будущих решений о методе. После просмотра результатов test
он перестаёт быть нетронутой выборкой для дальнейшей настройки; изменения алгоритма
нужно проверять на новом будущем периоде и явно указывать повторное использование
старого теста. Здесь не утверждается наличие обученной ML-модели.

## Что сравнивается

| Метод в CSV | Прогноз |
|---|---|
| `current` | `forecast_monthly_demand`: средний дневной прогноз × число дней целевого месяца |
| `last_month` | Количество предыдущего календарного месяца |
| `same_month_last_year` | Количество того же календарного месяца год назад |

У базовых методов нет замены отсутствующего месяца последним известным значением
и нет пересчёта по длине месяца. Если точный нужный месяц неизвестен, прогноз метода
недоступен. Текущий метод запускается при хотя бы одном известном месяце, как позволяет
его контракт. Менее трёх известных месяцев помечаются `short_history`; без истории
прогноз недоступен и не подменяется нулём.

`available` в CSV показывает отдельное покрытие каждого метода. Сравнивать их ошибки
как доказательство преимущества при разных строках нельзя. Для сравнения предназначены:

- `paired_last_month` — текущий и предыдущий месяц на одинаковых строках;
- `paired_same_month_last_year` — текущий и прошлогодний месяц на одинаковых строках;
- `common_all_models` — все три метода на общей подвыборке.

## Пропуски и смысл цели

Месячная ячейка — отчётные продажи, включая влияние возвратов. Это не измерение
скрытого спроса во время отсутствия товара и не готовое количество для заказа.

| Сценарий | Пустая ячейка существующей строки | Отрицательный месячный итог | Ошибка / отсутствующая строка |
|---|---|---|---|
| `unknown_blanks` | Неизвестно | Неизвестно | Неизвестно |
| `operational_zero_assumption` | 0 по допущению разреженной 1С-выгрузки | Ограничен нулём | Неизвестно |

Явный числовой ноль в обеих политиках остаётся наблюдением. Неизвестные факты
исключаются из оценки; неизвестные месяцы истории не передаются модели. Консервативная
политика может оценивать преимущественно месяцы с положительными продажами и давать
смещённое представление об ассортименте. Политика нулей отражает текущее операционное
допущение, которое должен подтвердить владелец данных. Даты ввода и вывода SKU неизвестны,
поэтому пустоту до первой продажи нельзя уверенно назвать отсутствием спроса.

Покрытие в JSON считается от всех пар «SKU из месячного отчёта продаж × месяц оценки».
Товары только из остатков не получают выдуманных продаж; их число показано отдельно.
Неизвестные единицы исключаются из количественных метрик и видны в отчёте. Это не
покрытие всех 3 907 товаров полного операционного каталога.

## Метрики

Для одной группы с известной единицей `error = prediction − actual`:

- **MAE:** среднее `abs(error)`, в единицах группы.
- **WAPE, %:** `100 × sum(abs(error)) / sum(actual)`.
- **Bias, %:** `100 × sum(error) / sum(actual)`; положительное значение — завышение.
- **Mean error:** среднее `error` в единицах группы.
- **Zero-target MAE:** ошибка на фактах, равных нулю; ложный положительный спрос остаётся видимым.
- **Macro SKU WAPE:** среднее WAPE по SKU с положительной суммой факта, с явным числом
  таких SKU. Это дополнительный показатель; он может быть чувствителен к малым объёмам.

При нулевой сумме факта WAPE и bias неопределены (`null` в смысле данных, пустое поле
CSV); MAE при этом остаётся определённой. Нулевые факты не удаляются ради улучшения
метрик. Метры, штуки, упаковки и комплекты не складываются в единый MAE или общий
объёмный WAPE. Сравнения выполняются внутри одной единицы и одинаковой подвыборки.

## Зафиксированный результат для текущих файлов

Проверено **3 017 SKU** месячных продаж: 2 463 IEK и 554 Systeme Electric.
Всего рассчитано 48 272 пары SKU × месяц × политика, записано 180 строк метрик.
Семь IEK SKU без единицы измерения отражены в покрытии, но не включены в метрики.
Это 8 месяцев двух независимых сценариев чтения одних и тех же фактов, а не 48 272
независимых наблюдения или новые данные.

Ниже **test, июль–август 2026**, WAPE на `common_all_models`; меньше — лучше.
Строки одной группы у всех трёх методов одинаковы. Таблица отражает сценарий
`operational_zero_assumption`, где пустота и отрицательный итог становятся нулём.

| Поставщик / единица | Пар SKU–месяц | Текущий | Предыдущий месяц | Тот же месяц год назад |
|---|---:|---:|---:|---:|
| IEK / шт | 4 458 | 39,23% | 34,65% | 43,93% |
| IEK / м | 274 | 62,53% | 72,60% | 94,70% |
| IEK / упак | 178 | 42,90% | 29,64% | 32,24% |
| Systeme Electric / шт | 1 108 | 25,47% | 18,58% | 36,29% |

В группе IEK «компл» обе цели равны нулю, поэтому WAPE не определён; MAE всех методов
равна нулю. Это не основание писать «точность 100%».

При консервативном `unknown_blanks` охват значительно меньше:

| Поставщик / единица | Всего кандидатов | Известных фактов | Общих пар трёх методов | WAPE текущего / предыдущего / прошлогоднего |
|---|---:|---:|---:|---|
| IEK / шт | 4 458 | 1 995 | 1 254 | 36,31% / 31,74% / 39,55% |
| IEK / м | 274 | 131 | 102 | 60,51% / 70,68% / 81,40% |
| IEK / упак | 178 | 92 | 67 | 41,07% / 27,15% / 30,42% |
| Systeme Electric / шт | 1 108 | 663 | 479 | 24,45% / 17,27% / 34,15% |

В этих тестовых исходниках нет явных числовых нулей: нули второго сценария появляются
по выбранной политике. Разницу между сценариями нельзя приписывать улучшению алгоритма.
Текущий метод проигрывает прогнозу предыдущего месяца в штуках и упаковках и выигрывает
в метрах на показанном тесте. Преимущество над простым базовым методом для всего
ассортимента **не подтверждено**. Оценка опубликована без настройки алгоритма по test.
Подробные MAE, bias, validation, отдельное и парное покрытие сохранены в CSV/JSON.

## Границы выводов

Это оценка функции прогноза на ретроспективных матрицах. Она не проверяет весь заказ
с очисткой оптовых покупок, компенсацией stockout, страховым запасом, MOQ и поставками.
Исторические снимки «как данные выглядели тогда» отсутствуют: поздние исправления
отчётов и отбор сохранившихся товаров нельзя исключить. Единицы взяты из текущего
справочника и служат группировкой метрик, а не прогнозным признаком.

Два тестовых месяца не доказывают устойчивую точность на год, экономию денег или
готовность к production. Даже если алгоритм проигрывает простому методу, отчёт
сохраняет результат. Следующий шаг — согласовать семантику пустот, получить новый
временной срез и проверить изменения на будущем периоде; не выбирать лучший метод
по уже увиденному test и не объявлять его независимой проверкой.
