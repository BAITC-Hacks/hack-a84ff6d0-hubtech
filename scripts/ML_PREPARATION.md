# Подготовка данных для месячного прогноза IEK

Запуск из корня проекта:

```bash
python -m pip install -r scripts/requirements-ml.txt
python scripts/prepare_ml_data.py --as-of 2026-09-23
```

Скрипт читает все шесть файлов из `IEK/`, сохраняет результаты в `data/ml/iek/` и не
изменяет исходники. Для других путей используйте `--input-dir` и `--output-dir`.
По умолчанию дата фиксирована для текущих выгрузок, а не зависит от сегодняшнего дня.
Повторный успешный запуск обновляет созданные CSV и отчёт в выбранной папке.

## Результаты

| Файл | Что содержит |
|---|---|
| `training_data.csv` | Известные неотрицательные месячные цели и признаки из прошлого; столбец `split` |
| `prediction_features.csv` | Признаки месяца после завершённой истории; готовность по `history_sufficient` |
| `monthly_panel.csv` | Все товары и месяцы, исходные продажи/остатки, статусы пропусков и обработанные значения |
| `products.csv` | Код, название, единица измерения, артикул поставщика |
| `transactions.csv` | Транзакции с исходным знаком, типом документа и номером строки Excel |
| `moq.csv` | Минимальные количества; неизвестный MOQ остаётся пустым, кратность не выдумывается |
| `in_transit.csv` | Отдельная строка для товара и поставки, количество и дата ожидаемого поступления |
| `provided_seasonality.csv` | Коэффициенты из файла; не используются при подготовке исторических признаков |
| `reconciliation.csv` | Сравнение месячных продаж и расходных накладных, включая несовпадающие суммы |
| `quality_issues.csv` | Некорректные значения, отрицательные количества, дубли |
| `preparation_report.json` | Правила, границы периодов, список признаков, счётчики и SHA-256 исходников |

Таблицы для закупок и raw-таблицы могут содержать строки позже исторического `--as-of`.
Они не являются входом исторической модели. Для обучения используйте только
`training_data.csv` и `feature_columns` из JSON. Остатки в матрице — начальные,
актуального свободного остатка в файле пути IEK нет.

## Правила очистки

По умолчанию:

- Пустые продажи остаются неизвестными. Они не превращаются в нулевой спрос.
- Отрицательные продажи сохраняются в `sales_qty_raw`, но исключаются из целей и лагов.
- Отрицательные остатки сохраняются в raw-поле, но не используются как признак наличия.
- Ошибка ячейки отличается от пустой ячейки. Даже при заполнении пропусков нулями ошибки остаются неизвестными.
- Пустой месячный отчёт для отсутствующего товара не заменяется нулями.
- Коды сохраняются текстом, включая ведущие нули, кириллицу и `_`.
- Дробные количества сохраняются. Разные единицы одного кода останавливают обработку.
- Разные месячные строки одного кода или противоречивые MOQ останавливают обработку.
- Совпадающие ограничения MOQ объединяются, даже если текст названия отличается.
- Одинаковые транзакции не удаляются автоматически: это могут быть реальные строки документа.
- Крупные продажи не исключаются автоматически. Отчёт сверки нужен до разметки опта.

После подтверждения смысла пустот и отрицательных значений партнёром можно явно включить:

```bash
python scripts/prepare_ml_data.py --as-of 2026-09-23 --blank-sales zero --negative-sales zero
```

`--negative-sales zero` ограничивает отрицательный месячный итог нулём только в модельном
значении. Это допущение об учёте возвратов, а не восстановление валового спроса.
`--blank-sales zero` применяется только к действительно пустой ячейке присутствующего
отчёта, в том числе до первых продаж: даты запуска товара неизвестны. Эти правила
нужно согласовать до интерпретации метрик модели. По умолчанию строки с неизвестной
целью исключены из обучения, поэтому покрытие оценки будет неполным.

## Временные границы

Для текущих выгрузок и `--as-of 2026-09-23` полная история заканчивается августом 2026.
В качестве ограничения полноты также используется день после последней транзакции:
перенос `--as-of` вперёд не сделает сентябрь в старой выгрузке завершённым.
Это консервативное ограничение, а не подтверждение полноты учётных данных.

Прогнозная строка относится к сентябрю 2026 и использует историю до августа. Это
прогноз полного сентября от его начала; доступные сентябрьские продажи намеренно
не используются. Для оперативного прогноза оставшейся части месяца нужен отдельный
сценарий. При старых выгрузках прогнозный месяц не переносится автоматически на сегодня.

В обучающей таблице целевой месяц T использует только продажи месяцев < T:
`lag_1/2/3/6/12`, средние за 3/6 месяцев, стандартное отклонение за 6 месяцев,
число наблюдений, доли пропусков/нулей, длину истории и начальный остаток прошлого месяца.
Средние считаются по известным значениям; рядом сохранено их количество.
Минимум — 3 известных месяца в прошлом (`--min-history`).

Границы общие для всех товаров и отсчитываются от прогнозного месяца:

- `train`: до января 2026;
- `validation`: январь–июнь 2026 (6 месяцев);
- `test`: июль–август 2026 (2 месяца).

Это основа последовательной проверки прогноза на один месяц: факт июля разрешён для
прогноза августа только после завершения июля. Такой набор не предназначен для
одновременного прогноза сразу двух месяцев из июня. Код обучения должен соблюдать
эти границы; для каждой проверки по времени заново обучайте модель на доступном прошлом.

Готовые коэффициенты сезонности, текущие MOQ и поставки не включаются в признаки.
Сезонность уже содержит сведения из 2026 и прогнозные компоненты. Использование её
сегодняшней версии для теста в прошлом привело бы к утечке будущего.

## Загрузка для будущего обучения

```python
import json
import pandas as pd

folder = "data/ml/iek"
with open(f"{folder}/preparation_report.json", encoding="utf-8") as file:
    report = json.load(file)

data = pd.read_csv(
    f"{folder}/training_data.csv",
    dtype={"sku": "string", "unit": "string"},
    parse_dates=["target_month"],
)
train = data.loc[data["split"] == "train"]
X_train = train[report["feature_columns"]].copy()
y_train = train[report["target_column"]]
# Код товара — категория, а не число. Кодирование категорий подбирается
# и обучается только на train, затем применяется к validation/test.
```

`split`, `target_qty` и raw-количества нельзя добавлять к X. У товара может быть мало
истории: для `history_sufficient=False` нужен отдельный fallback, а не обещание
надёжного ML-прогноза. Обучение модели и оценка метрик в этот скрипт не входят.
