# Обогащение справочника каталогом ekt.kz

## Назначение

Публичный каталог добавляет **товарные категории, подкатегории, характеристики и ссылки на карточки** к уже известным артикулам учётных выгрузок. Это помогает менеджеру отбирать и узнавать товары, особенно когда внутренняя категория отсутствует или представлена кодом.

Источник чисел для закупки — учётные Excel/CSV. Обогащение не меняет продажи, остатки, приходы, единицы измерения, цены, MOQ, кратность и сроки поставки. Оно не восстанавливает клиентов или периоды отсутствия товара.

## Разделение получения и использования

```mermaid
flowchart LR
    S["Публичные карточки ekt.kz"] --> C["scripts/sync_ekt_catalog.py"]
    C --> J["Локальный JSON"]
    I["Учётный каталог: код 1С"] --> M["Точное сопоставление SKU"]
    J --> M
    M --> A["Фильтры и карточки в API/UI"]
```

Синхронизация — отдельный запуск [`backend/scripts/sync_ekt_catalog.py`](../backend/scripts/sync_ekt_catalog.py). Расчёт и экспорт работают с сохранённым JSON и **не обращаются к сайту**. Обновление карточек не меняет ранее сохранённый расчёт и серверные решения заказа. При переносе `baitc/frontend` (`5a0ace2`) обогащение основной ветки сохранено и возвращено в новый интерфейс; старый код ветки не заменяет учётный импорт и сопоставление EKT.

## Файл и контракт версии 1

Путь по умолчанию: `data/ekt/catalog.json`. `EKT_CATALOG_ENABLED=true` включает обогащение; `false`, `0`, `no`, `off` отключают. `EKT_CATALOG_PATH` задаёт абсолютный путь или относительный от корня проекта. Сейчас подключение реализовано в `ExcelDataSource.load`; CSV и synthetic не обращаются к этому справочнику. Схема содержит `schema_version: 1`, источник `source`, время получения `fetched_at`, сведения о проходе `crawl` и массив `products`.

Иллюстрация структуры; значения ниже не являются результатом выгрузки:

```json
{
  "schema_version": 1,
  "source": "https://ekt.kz/",
  "fetched_at": "2026-09-23T00:00:00Z",
  "crawl": {},
  "products": [
    {
      "sku": "0000123_",
      "supplier_sku": "ARTICLE-EXAMPLE",
      "brand": "Бренд",
      "name": "Наименование на сайте",
      "product_category": "Основной раздел каталога",
      "product_subcategory": "Подраздел",
      "product_url": "https://ekt.kz/catalog/example/",
      "product_attributes": {"Характеристика": "Значение"},
      "fetched_at": "2026-09-23T00:00:00Z",
      "source_kind": "product"
    }
  ]
}
```

| Поле продукта | Назначение |
|---|---|
| `sku` | Строковый код для точного сопоставления с `Dataset.catalog.sku` |
| `supplier_sku` | Артикул производителя/поставщика с сайта, отдельный от внутреннего кода |
| `brand`, `name` | Публичные название бренда и товара с сохранением происхождения |
| `product_category` | Основной товарный раздел каталога; не внутренний код категории 1С |
| `product_subcategory` | Более узкий подраздел |
| `product_url` | Источник карточки |
| `product_attributes` | Словарь характеристик; описательные данные, а не расчётные ограничения |
| `fetched_at` | Время получения карточки; не дата обновления учётных остатков |
| `source_kind` | Дополнительная метка сборщика: `listing` — страница списка, `product` — подробная карточка; runtime-валидатор её не использует |

`sku`, `name`, `product_category`, `product_url` и временные метки должны быть непустыми строками. `supplier_sku`, `brand` и `product_subcategory` могут быть пустыми строками. `product_attributes` — словарь строк; пустой `{}` допустим и означает отсутствие собранных характеристик. Корневой `source` допускает только HTTPS-корень `ekt.kz`/`www.ekt.kz`, ссылки карточек — HTTPS на том же домене с путём `/catalog/`. Время передаётся в ISO-формате с компонентом времени.

Поля `name` и `supplier_sku` с сайта сохраняются в JSON для сверки, но не заменяют учётные значения. При заполненном и отличающемся артикуле либо известном несовместимом бренде связь отклоняется. Бренд сайта отображается отдельно как `product_brand`.

Верхнеуровневый `crawl` содержит фактические параметры и результаты синхронизации: `target_count`, `observed_this_run`, доступные/прочитанные страницы разделов, число подробных карточек, запросов и попаданий в кеш, лимиты, задержку, `robots_checked`, `failures` и `quarantined_skus`. Корневой `fetched_at` относится к сборке снимка; у каждого товара сохранено собственное время получения HTML, в том числе при использовании кеша. Покрытие следует оценивать по полученному файлу и метаданным API, а не по общему числу карточек сайта.

## Сопоставление и конфликты

- Связь выполняется по **точному строковому `sku`**. Ведущие нули и подчёркивания сохраняются; `0000123_`, `0000123` и `123` не объявляются одним товаром.
- Название товара, похожий артикул или совпадающий бренд сами по себе не подтверждают связь. Нечёткое автоматическое объединение не применяется.
- Повторяющийся `sku` внутри входного JSON отклоняется валидатором. Сборщик может встретить одну и ту же карточку в нескольких разделах: одинаковая ссылка и согласованный артикул дают одну запись. Разные карточки или артикулы для одного кода помещаются в `crawl.quarantined_skus`; они не объединяются автоматически.
- Исходная внутренняя `category` остаётся отдельной. Товарный фильтр использует `product_category`, подраздел — `product_subcategory`.
- Несопоставленная позиция продолжает участвовать в расчёте по имеющимся учётным данным; отсутствие карточки не доказывает отсутствие товара или спроса.
- Значения характеристик вида «упаковка», «наличие» или «цена» не переопределяют `pack_size`, `on_hand` или цену учётной системы.

## API и интерфейс

После входа `GET /api/meta` дополняется `product_categories` для отдельного фильтра и сводкой `data_quality.catalog_enrichment` о покрытии и состоянии локального справочника. В `POST /api/recommend` есть необязательный `product_category`; прежняя `category` сохраняет смысл внутренней категории. Новый UI передаёт фильтр в постоянное фоновое задание, затем получает сохранённый заказ по его `order_id`.

Строка рекомендации несёт `product_category`, `product_subcategory`, `product_brand`, `product_url`, `product_attributes` и `catalog_fetched_at`. Внутренние `name`, `category`, `unit` и `supplier_sku` сохраняются. Эти поля объясняют происхождение описательных данных. Они не являются входом числовой формулы прогноза. При изменении товарного фильтра меняется набор выбранных SKU, а не спрос отдельного SKU.

В новом интерфейсе сохранены фильтр товарной группы, дополнительные описания, происхождение и безопасная ссылка на HTTPS-карточку EKT. Метаданные API отдают разрешённые сводные поля, без серверных путей и сырых диагностических текстов. При экспорте `/api/orders/{id}/export` товарные поля берутся из сохранённого расчёта вместе с текущей revision и решениями. Замена JSON либо смена фильтра без нового расчёта не переписывает старый заказ.

Отчёт `data_quality.catalog_enrichment` включает:

- `status`: `disabled`, `missing`, `invalid`, `empty_catalog`, `partial` или `loaded`;
- `source`, `fetched_at`, `total_catalog`, `web_products`, `valid_products`;
- `matched`, `unmatched`, `conflicts`, `invalid_products`;
- `duplicate_skus`, `duplicate_products`, `unknown_brand_matches`;
- `crawl_quarantined`, `crawl_failures`, `crawl_coverage` — сводка аудита сборщика без сырых URL и текстов ошибок;
- `conflict_reasons`: `supplier_sku`, `brand`, `duplicate_web_sku`, `duplicate_base_sku`.

`matched / total_catalog` — покрытие учётного каталога. `loaded` означает применение полного валидного набора к текущему каталогу, а `partial` — наличие пропусков или отклонённых записей. Отсутствующий или некорректный файл не ломает основной расчёт: он продолжается с учётными данными и предупреждением.

## Обновление и проверка

Из корня проекта:

```bash
cd backend
./.venv/bin/python -m scripts.sync_ekt_catalog --help
```

Пример ограниченного прохода из `backend`:

```bash
./.venv/bin/python -m scripts.sync_ekt_catalog --max-pages 120 --max-details 80 --delay 1.0 --timeout 20
```

Скрипт читает robots.txt и sitemap, запрашивает только разрешённые публичные URL каталога без параметров поиска и сохраняет точные совпадения с известными кодами. `--max-pages` и `--max-details` ограничивают объём работы; минимальный `--delay` — 0.5 секунды. `--output` задаёт выходной JSON. HTML кешируется в `backend/.cache/ekt` на 7 дней; `--refresh` позволяет обновить страницы. Цены и изображения не собираются. Запись JSON выполняется атомарно при наличии найденных совпадений, чтобы не заменить справочник пустым результатом неудачного прохода.

Часть записей может прийти только из списка (`source_kind=listing`) и не иметь характеристик. Ограниченный проход не означает сбор всех товаров или 100% покрытия.

Точные параметры сбора и ограничения запуска задаются CLI скрипта. После синхронизации следует проверить `source`, `fetched_at`, `crawl`, покрытие известных SKU, пропуски и конфликты. Изменение локального файла должно проверяться отдельным авторизованным запросом `/api/meta`; уже сохранённый расчёт для экспорта остаётся неизменным.

Обновление не создаёт интеграцию с 1С и не подтверждает свежесть её данных. Для неё см. [ИНТЕГРАЦИЯ_1С.md](ИНТЕГРАЦИЯ_1С.md).

## Зафиксированный результат ограниченного прохода

Снимок [`data/ekt/catalog.json`](../data/ekt/catalog.json) собран **2026-09-23T10:25:22Z**. Это дата сборки файла; время получения каждой записи указано отдельно в её `fetched_at` и может быть старше при использовании кеша. Ниже приведён результат этой версии, а не обещание покрытия последующих выгрузок.

Проход выполнен с `--max-pages 160 --max-details 80`. Значение `--max-pages` по умолчанию остаётся 120.

| Этап | Результат |
|---|---|
| Прочитанные страницы разделов / попытки подробных карточек | 160 / 80 |
| Наблюдавшиеся совпадающие SKU | 1 000 |
| Коды на ручной проверке (`crawl.quarantined_skus`) | 200: разные URL или артикулы для одного кода |
| Записи в опубликованном JSON | 800: 78 из подробных карточек, 722 из списков |
| Применено к учётному каталогу | **773 из 3 907 SKU — около 19,8%** |
| Без применённого обогащения | 3 134 SKU, включая отклонённые и не найденные |
| Конфликты артикула при применении JSON | 27 (`conflict_reasons.supplier_sku`) |
| Некорректные записи JSON | 0 |
| Товарные группы в фильтре | 9 |
| Строки полного расчёта с обогащением | 118 из 430 |

Статус — **`partial`**. Сбор не охватывает весь сайт, все карточки или все 3 907 учётных SKU. У записей из списков характеристики могут быть пустыми; наличие категории не означает подробного прочтения карточки.

`crawl_failures = 205` — это число записей аудита: 200 конфликтов сопоставления, одна ошибка страницы раздела и четыре ошибки подробных карточек. Это **не 205 недоступных страниц**. Для разбора используется полный `crawl` в JSON; API отдаёт сводные счётчики.

Список `crawl.quarantined_skus` сохраняется между проходами. Возврат кода в сопоставление требует ручной проверки и явного разрешения конфликта; повторный запуск сам его не снимает. Переходы HTTP не могут вывести запрос за разрешённые адреса и правила доступа.

Сравнение расчёта с включённым и выключенным справочником сохранило **430 строк** (429 с положительным количеством; IEK — 339, Systeme Electric — 91) и числовые рекомендации. Различаются описательные поля и доступный отбор по товарным группам.

При первоначальной проверке снимка были выполнены регрессии импорта/сопоставления, расчёта с включённым/выключенным EKT и экспорта, а также проверки интерфейса. После интеграции нового frontend актуальные команды находятся в [README](../README.md), результаты — в [отчёте по критериям](ОТЧЁТ_ПО_КРИТЕРИЯМ.md); историческая проверка снимка не заменяет их.

Исторический пример проверки до переноса frontend: в скачанном через интерфейс Excel для SKU `010500103_` сохранены рекомендация 206, ручное количество 210, утверждение, товарная группа и URL карточки. После выбора другого фильтра без пересчёта экспорт сохранил группу исходного расчёта «Низковольтная аппаратура». Тогда проверочные правки и подтверждение были сброшены. Теперь постоянные решения хранятся на сервере; их состояние и скачивания проверяются по заказу и revision.

## Города публичного сайта

На предоставленном экране выбора города перечислены Алматы, Астана, Шымкент, Тараз, Атырау, Актау, Караганда, Талдыкорган и Усть-Каменогорск. Это география сайта; снимок `data/ekt/catalog.json` не содержит достоверных продаж, остатков, резервов или сроков по этим городам. Город не используется как дополнительный источник количеств и не создаёт склад автоматически.

Обогащение продолжает сопоставлять справочные карточки с существующими SKU. Региональный расчёт требует учётных данных конкретного склада: [ГОРОДА_И_СКЛАДЫ.md](ГОРОДА_И_СКЛАДЫ.md). Подготовленные CSV ветки `alish` происходят из прежних IEK-выгрузок и тоже не добавляют региональную историю: [АУДИТ_ВЕТКИ_ALISH.md](АУДИТ_ВЕТКИ_ALISH.md).

[BACKTEST.md](../scripts/BACKTEST.md) публикует измеренную ошибку месячного прогноза на отчётах IEK/Systeme и сравнение с простыми методами. Описательные поля EKT в этот прогноз не входят. Покрытие 773/3 907 не является точностью модели, а улучшение внешнего каталога само по себе не доказывает снижение дефицита или экономию. Общее превосходство текущего метода над базовым прогнозом на всём ассортименте не подтверждено.
