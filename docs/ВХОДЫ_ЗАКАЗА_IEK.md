# Подготовка входов заказа IEK

Реализованы этапы 1–2: сохранённые настройки и проверяемая таблица по товарам.
Это вход для последующей проверки прогноза и расчёта заказа. Скрипт не формирует
количество заказа, не утверждает и не отправляет заказ, не меняет работающий API.

## Подтверждённые параметры

Файл `config/iek_replenishment.json`:

| Параметр | Значение |
|---|---|
| Поставщик | IEK |
| Склад | Алматы |
| Срок поставки | 21 день |
| Период проверки | 14 дней |
| Уровень сервиса | 95% |
| Горизонт | 35 дней |

Пользователь подтвердил склад, срок, период проверки и уровень сервиса.
Дата расчёта для предоставленных файлов — 23.09.2026. Интервал ожидаемых поступлений:
с 23.09.2026 включительно до 28.10.2026 не включительно.

Смысл пустых и отрицательных продаж не подтверждён. Исходные значения сохраняются,
пустоты не превращаются в нули, отрицательные количества не становятся положительными.
В модельном поле неподтверждённые значения остаются неизвестными.

Настраиваемые технические пороги свежести: свободный остаток не старше одного дня,
снимок пути не старше семи дней. Эти пороги можно изменить в конфигурации.

## Запуск

Из корня проекта:

```bash
python -m pip install -r scripts/requirements-ml.txt
python scripts/prepare_order_inputs.py
```

По умолчанию заново читаются шесть Excel через существующую ML-подготовку, затем
собирается снимок в `data/orders/iek/`. Исходные Excel не меняются.
Для повторной сборки без обработки исходников:

```bash
python scripts/prepare_order_inputs.py --reuse-prepared
```

При этом проверяются дата, правила очистки и SHA-256 каждого из шести исходников.
CSV в `data/ml/iek/` должны оставаться машинными результатами без ручных правок.
При сомнении используйте обычный запуск для пересоздания. Повторный запуск обновляет
четыре выходных файла в выбранной папке, а не пользовательские дополнительные входы.

## Результат

- `order_inputs.csv`: одна строка на товар; настройки, история, текущий свободный остаток,
  последний известный начальный остаток, MOQ, кратность, пересчёт единиц и поступления.
- `arrival_schedule.csv`: отдельная строка на товар и поставку, ETA и причина использования/исключения.
- `provided_seasonality.csv`: коэффициенты поставщика как отдельный справочный источник.
- `input_report.json`: зафиксированные настройки, источники с хешами, статистика и недостающие поля.

`on_hand` — только актуальный свободный остаток из дополнительной выгрузки.
`historical_opening_stock` и `historical_stock_as_of` — последний известный начальный
остаток из месячного отчёта. Он никогда не подставляется вместо `on_hand`.
Настоящий свободный остаток 0 сохраняется как 0.

`reported_in_transit_qty` — сообщённое количество внутри горизонта в единицах исходника.
`in_transit` — количество в складских единицах после явно заданного пересчёта.
При неизвестном пересчёте второе поле остаётся пустым. Просроченные поступления
выводятся для проверки; поступления после горизонта не уменьшают потребность.
Поздняя дата ETA сама по себе не доказывает отсутствие дефицита до её наступления:
следующий этап должен учитывать календарь из `arrival_schedule.csv`.

Если товар есть в актуальном каталоге пути, но для него не указаны количества,
это трактуется как отсутствие зарегистрированных поступлений в предоставленном
отчёте. Отсутствие самого товара в каталоге пути означает неизвестное значение.
ETA «поступление до» — крайняя плановая дата, а не фактическая дата приёмки.

`input_status`:

| Статус | Значение |
|---|---|
| `incomplete` | Нет хотя бы одного необходимого числового входа или единицы измерения |
| `review` | Числовые входы есть, но остались неподтверждённые правила или расхождения |
| `ready` | Входы заполнены и нет обнаруженных причин проверки |

Поля `missing_fields` и `review_reasons` содержат причины. Статус `ready` означает
готовность входов к расчёту, а не качество будущего прогноза или утверждение заказа.
В текущих исходниках нет актуального свободного остатка IEK и отдельной кратности,
поэтому отсутствие готовых строк — ожидаемый результат проверки.

## Дополнительные входы

Пустые шаблоны находятся в `config/templates/`. Скопируйте их в свои файлы и заполните
реальными значениями. Заголовки английские; код товара хранится как текст.

`current_stock.csv`:

| Поле | Значение |
|---|---|
| `sku` | Код 1С |
| `warehouse` | Склад, для текущего расчёта Алматы |
| `unit` | Складская единица измерения |
| `as_of` | Дата снимка YYYY-MM-DD |
| `free_stock` | Доступное количество после резервов, не общий остаток |

Из нескольких дат выбирается последняя не позднее даты расчёта. Будущие,
устаревшие, отрицательные остатки и несовпадение единиц не используются.
Повтор одного кода, склада и даты останавливает сборку, чтобы не удвоить запас.

`purchase_rules.csv`:

| Поле | Значение |
|---|---|
| `sku` | Код 1С |
| `order_unit` | Единица заказа поставщику |
| `stock_units_per_order_unit` | Сколько складских единиц в одной единице заказа |
| `pack_size` | Кратность в единицах заказа; 1 — только если это подтверждённое правило |
| `min_order_qty` | Необязательное уточнение MOQ; при пустоте берётся значение из MOQ Excel |
| `transit_unit` | Единица количеств из отчёта о пути |
| `stock_units_per_transit_unit` | Сколько складских единиц в одной единице пути |

Закупочная и транспортная единицы могут различаться: товар могут заказывать бухтами,
а путь уже указывать метрами. Эти коэффициенты задаются отдельно. Если названия единиц
совпадают, коэффициент должен быть 1. Неизвестные коэффициенты не выдумываются.
Минимум IEK не считается автоматически кратностью. Неизвестный MOQ не заменяется единицей.

Запуск с дополнительными входами:

```bash
python scripts/prepare_order_inputs.py \
  --current-stock "path/to/current_stock.csv" \
  --purchase-rules "path/to/purchase_rules.csv"
```

## Связь с дальнейшей работой

Далее нужна проверка прогноза на отложенных месяцах и оценка страхового запаса.
После этого прогноз за 35 дней связывается с `on_hand`, календарём поступлений,
MOQ и кратностью из подготовленного снимка. Итоговые количества считаются в
согласованных единицах; метры, штуки и упаковки в один физический итог не складываются.
Готовые коэффициенты сезонности нельзя использовать в историческом тесте без
пересчёта по доступному на тот момент прошлому.

Эти CSV не являются прямой заменой `DATA_SOURCE=csv` существующего API: адаптер
подключается на следующем этапе вместе с расчётом. Существующие backend-настройки
21 день / 14 дней / 95% совпадают с подтверждёнными значениями, но новый JSON
сейчас читается сборщиком входов, а не приложением FastAPI.

Проверки:

```bash
python -m unittest discover -s scripts -p 'test_prepare_order_inputs.py' -v
```
