# Демонстрация Umytpa: от исходных данных до сохранённого заказа

Сценарий рассчитан примерно на **7–8 минут** после подготовки стенда. Его можно использовать для представителя компании, жюри или сотрудника закупок. Он показывает текущий интерфейс и проверяемые действия; наличие сценария не означает, что выступление состоялось или оценено. **20 баллов за презентацию, демо и ответы остаются неоценёнными до живого выступления.**

Задача показа: продемонстрировать «данные → расчёт → объяснение → ручное решение → сохранение → Excel» и честно обозначить границы. Для промышленной приёмки дополнительно требуются сценарии [ТЗ платформы](ТЗ_платформы.md), [эксплуатационные проверки](DEPLOY.md) и проверка заказа с сотрудником компании.

## 1. Подготовка до встречи

Используйте отдельный локальный демонстрационный стенд. Подготовка среды, установка пакетов и создание пользователя не входят в семь минут. Полная инструкция, Linux-развёртывание, резервирование и восстановление — [DEPLOY.md](DEPLOY.md).

Для нового окружения из корня проекта:

```bash
cd backend
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
cp .env.example .env
```

Если `backend/.env` уже существует, внесите нужные значения в него, сохранив остальные настройки. Не заменяйте действующую конфигурацию этой командой. Настройки демонстрации:

```text
APP_ENV=development
APP_ORIGIN=http://127.0.0.1:5173
APP_DB_PATH=.cache/demonstration.sqlite3
DATA_SOURCE=excel
DATA_DIR=.
DATA_AS_OF=2026-09-23
SERVICE_LEVEL=0.95
REVIEW_PERIOD_DAYS=14
IEK_LEAD_TIME_DAYS=21
SYSTEME_LEAD_TIME_DAYS=35
OPENAI_API_KEY=
```

Здесь относительный `APP_DB_PATH` рассчитан на запуск **CLI, API и worker из `backend/`**. Все три должны открыть одну демонстрационную БД. `DATA_DIR` разрешается от корня репозитория. Реальные исходные файлы остаются только для чтения в `IEK/` и `Systeme electric/`; данные сайта EKT — необязательный локальный справочник `data/ekt/catalog.json`.

Создайте первого администратора один раз; пароль вводится скрыто. Этот блок также выполняется из корня репозитория:

```bash
cd backend
.venv/bin/python -m app.manage migrate
.venv/bin/python -m app.manage create-admin --username demo-admin
```

Запустите три процесса в отдельных терминалах, каждый начиная от корня проекта:

```bash
# Терминал 1 — API
cd backend
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8017 --no-access-log
```

```bash
# Терминал 2 — обработчик расчётов
cd backend
.venv/bin/python -m app.worker
```

```bash
# Терминал 3 — интерфейс
cd frontend
npm ci
npm run dev -- --host 127.0.0.1
```

Откройте [локальный интерфейс](http://127.0.0.1:5173). Используйте именно `127.0.0.1`, как в `APP_ORIGIN`. Проверьте готовность:

```bash
curl --fail http://127.0.0.1:8017/api/ready
```

До встречи войдите администратором, в разделе **«Команда»** создайте пользователя с ролью менеджера и выполните пробный расчёт. Для основного показа войдите менеджером. Сохраните ссылку на пробный заказ как резерв на случай длительного расчёта; открывая её, прямо скажите, что это ранее сохранённый результат, а не завершившееся только что задание.

Проверьте, что рядом с интерфейсом можно открыть скачанный XLSX, терминал с контрольными проверками и [BACKTEST.md](../scripts/BACKTEST.md). Пароли, `.env` и исходные файлы с лишними служебными данными на экран не выводите.

**Разница между кнопками:** отметка строки затрагивает выбранную строку; **«Утвердить поставщика»** действует на все допустимые позиции поставщика, включая скрытые поиском и другими страницами. Экспорт также учитывает все подходящие сохранённые строки, а не только видимую страницу. Для файла с одной контрольной строкой не используйте групповое утверждение.

Слово **«утверждение»** в текущем UI означает личное подтверждение строк менеджером с серверной проверкой. Это ещё не независимое согласование другим руководителем. Скачанный файл не отправляется поставщику автоматически и не создаёт документ в 1С.

### Объяснение и EKT

В диалоге **«Почему?»** числовая раскладка относится к первоначальной рекомендации 6 989 м. После ручной правки 6 990 м она не должна притворяться обоснованием нового машинного расчёта.

Раздел **«Справочник товара»** может показывать группу, бренд, характеристики и ссылку EKT. Если для выбранного SKU совпадения нет, интерфейс прямо сообщает об этом; можно открыть другую сопоставленную позицию. Не обещайте EKT-карточку для каждого товара. Описание сайта не заменяет учётные продажи, остаток, единицы, MOQ и срок поставки. Переход на внешнюю карточку для демонстрации формулы не нужен.

## 4. Проверка ошибки и конфликта

**Незавершённое количество:** очистите поле контрольной строки. Покажите **«Есть незавершённый ввод»** и недоступный экспорт. Пустота не приравнивается к нулю. Введите обратно 6 990 и дождитесь сохранения. Ноль, введённый явно, исключает позицию из заказа; это отдельное осознанное действие.

**Конфликт ревизий:** выполняйте на демонстрационном заказе в двух вкладках одного аккаунта.

1. Откройте один заказ в обеих вкладках и дождитесь одинаковой сохранённой версии.
2. Во вкладке A измените контрольную строку на 6 991, дождитесь сохранения.
3. Не обновляя B, измените там строку на 6 992. Дождитесь **«Заказ изменён в другой сессии»**.
4. Покажите **«Ваш ввод» / «На сервере»**. Автосохранение остановлено; локальное изменение не объявляется записанным.
5. Для короткого сценария выберите **«Принять серверную версию»**. Затем верните 6 990 и дождитесь сохранения. При изменении количества прежнее утверждение снимается; подтвердите строку заново, если нужен новый утверждённый Excel.

Вариант **«Перенести мои изменения»** требует просмотра сравнения: изменённые пользователем поля применяются к показанной версии сервера. Это явный выбор разрешения конфликта, а не автоматическое восстановление старого утверждения. Показ в двух вкладках проверяет конкуренцию ревизий; он не демонстрирует ещё не реализованный процесс согласования руководителем.

## 5. Контрольные доказательства Must-have

Из `backend/`:

```bash
OPENAI_API_KEY='' .venv/bin/python -m tests.validate_must_have
```

| Группа проверки | Что подтверждает контрольный набор |
|---|---|
| MH1 — источники | 14 точных проверок: объёмы, остаток, допустимый/поздний ETA, срок/связь поставщика, MOQ/кратность, категория как фильтр; месячные и транзакционные объёмы не складываются дважды |
| MH2 — сезонность и рост | Сезонность на одном наборе меняет заказ **70 → 140**; известный линейный рост даёт **203 в день**, заказ **1 421** |
| MH3 — отсутствие товара | Месячная ветка **40 → 70**, дневная **42 → 70**; обе добавляют **200** по явно переданному периоду отсутствия |
| MH4 — крупный клиент | Десять документов одного клиентского дня исключают суммарно **200** один раз; регулярный заказ остаётся **70** |
| MH5 — группировка и объяснения | Два поставщика, контрольные количества **70/140**, объяснение каждой строки |

В приложенных Excel **нет точных stockout-интервалов и клиентских ID**. На них нельзя показывать синтетические +200 как восстановленный реальный спрос. Документные номера остаются пригодны для документной детекции. Месячная компенсация содержит явные допущения; весь метод — [ML_И_ДАННЫЕ.md](ML_И_ДАННЫЕ.md). Зелёные контрольные проверки не заменяют оценку точности, согласование исходных политик или официальный допуск организатора.

## 6. Ответы на ожидаемые вопросы

| Вопрос | Ответ по текущей реализации |
|---|---|
| Нужна ли установленная 1С для запуска? | Нет: сервис читает переданные Excel/CSV. Для ежедневного обмена нужен согласованный механизм выгрузки. Создание заказа обратно в конкретной конфигурации 1С не реализовано; XLSX — файл для проверки и дальнейшей передачи. |
| Всё взяли с ekt.kz? | Нет. Количества — из учётных файлов; сайт дополняет описание и фильтрацию по товарным группам. Сетевой парсинг не выполняется при расчёте заказа. |
| Здесь обученная ML-модель? | Нет. Есть объяснимый прогноз, подготовка исследовательских данных `alish` и отдельный backtest. LLM при явном включении меняет только текст объяснения. |
| Прогноз лучше простого прошлого месяца? | Общее преимущество не подтверждено. На test июля–августа текущий метод выигрывает в метрах IEK, но проигрывает предыдущему месяцу в штуках/упаковках. Есть сравнимые группы, политики пропусков и ограничения: [BACKTEST.md](../scripts/BACKTEST.md). |
| Почему только Алматы, если на сайте девять городов? | Названия филиалов не являются рядами продаж и остатками. Реальные выгрузки подтверждают Алматы; для новых складов нужны собственные данные и устойчивые идентификаторы. |
| Сколько денег или времени уже сэкономили? | Измеренного результата пилота пока нет. Ни число рекомендаций, ни скорость вычисления не равны экономии закупщика. Ниже — шаблон измерения без вымышленных результатов. |
| Можно работать нескольким сотрудникам? | Есть личный вход, роли `admin`/`manager`, собственные заказы менеджера, сохранение, ревизии и аудит. У администратора шире доступ. Пять бизнес-ролей, области по складам и независимое согласование остаются целевыми требованиями. |
| Готово ли всё к production? | Есть рабочая сервисная основа, worker и эксплуатационные инструкции. Требуются приёмка на целевом сервере, подтверждённые свежие данные/условия, процесс согласования, границы доступа, резервирование и измеренная нагрузка. Текущий worker выполняет одну задачу за раз. |
| Можно нажать «заказать» и товар сам приедет? | Нет. Сервис готовит объяснимый заказ и файл. Решение, проверка поставщика, отправка и дальнейший учёт остаются частью процесса компании. |
