# Концепция системы автономного пополнения для дистрибьюторов РК

> HackAlem AI · трек 05 · Логистика. Кейс ТОО «Электрокомплект».

---

## 1. Введение и целеполагание

Электротехнические дистрибьюторы РК (ЭКТ и аналогичные) держат тысячи артикулов от нескольких поставщиков с разными сроками поставки и MOQ. Пополнение считается вручную в Excel — редко, без учёта сезонности и упущенного спроса. Итог: **замороженный капитал** в избыточных запасах и **упущенные продажи** из-за дефицита.

Цель системы — превратить закуп из ручного расчёта в **полуавтономный процесс**: система по запросу считает потребность по выгрузкам 1С и предлагает заказ, а человек утверждает. Непрерывное получение учётных данных и расчёт по расписанию — последующее развитие. Это снижает издержки хранения, сокращает дефицит и делает решения объяснимыми и воспроизводимыми.

Тема созвучна повестке РК: логистика и запасы — прямой фактор себестоимости и доступности товаров. Первоисточник кейса — [../relly-problem.md](../relly-problem.md).

## 2. Роли (кадровая вертикаль закупа)

```mermaid
flowchart TD
    Z["Менеджер отдела закупа<br/>(основной пользователь)"] -->|запускает расчёт,<br/>корректирует, утверждает| SYS["Сервис автозаказов"]
    R["Руководитель закупа<br/>(целевая роль)"] -->|утверждение крупных заказов,<br/>лимиты бюджета| SYS
    SYS -->|заказ| P["Поставщики: IEK · Systeme Electric"]
```

- **Менеджер закупа** — запускает расчёт по складу/категории, проверяет обоснование, корректирует количества, утверждает.
- **Администратор** — управляет личными аккаунтами и видит все заказы; дополнительного этапа согласования не вводит.
- **Руководитель** (Roadmap) — контроль крупных заказов, лимиты, отчётность.

В текущем внутреннем сервисе работают роли manager/admin, личный вход, постоянные заказы и журнал решений. Отдельный этап согласования руководителем остаётся за пределами версии (см. [БЭКЕНД.md](БЭКЕНД.md)).

## 3. Модель данных запасов

Логика пополнения строится на связке:

```mermaid
flowchart LR
    SUP["Поставщик<br/>срок поставки, MOQ"] --> SKU["Артикул (код 1С)<br/>категория, кратность"]
    SKU --> DEM["Спрос<br/>месячные итоги + транзакции"]
    SKU --> STK["Остаток + товары в пути"]
    DEM & STK --> NEED["Потребность к заказу"]
```

**Принятый основной источник количества:** сводные месячные отчёты 1С задают объём спроса до уточнения расхождений с партнёром; их большая точность пока не доказана; транзакции применяются для выявления исключительного опта. При расхождении сумм крупные заказы в несогласованных месяцах не вычитаются — чтобы не стереть реальный спрос.

---

## 4. Интеллектуальное ядро

1. **Очистка спроса** — исключение разового опта после сверки отчётов; компенсация упущенного спроса в дневном режиме при явных интервалах отсутствия. В текущих реальных файлах таких интервалов нет.
2. **Прогноз** — уровень × сезонность месяца × тренд (объяснимая декомпозиция).
3. **Потребность** — точка заказа с покрытием на `срок поставки + период проверки` и страховым запасом по уровню сервиса.
4. **Обоснование** — LLM/шаблон по каждой строке; человек-в-контуре.

Подробно — в [ML_И_ДАННЫЕ.md](ML_И_ДАННЫЕ.md).

## 5. Сквозной процесс: от выгрузки до заказа

```mermaid
flowchart LR
    A["Выгрузка 1С (xlsx)"] --> B["Импорт + контроль качества"]
    B --> C["Расчёт потребности по SKU"]
    C --> D["Заказ по поставщикам + обоснование"]
    D --> E["Проверка и утверждение менеджером"]
    E --> F["Excel для сверки и передачи"]
    F --> G["Отправка поставщику (вручную)"]
```

**Ограничение принципа:** система никогда не отправляет заказ поставщику автоматически — только после подтверждения ответственного сотрудника.

---

## 6. Масштабирование концепции

- **Мультипоставщик / мультисклад** — модель уже разделяет расчёт по `(sku, warehouse)` и поставщикам.
- **Другие дистрибьюторы** — подключение через новый `DataSource` без изменения ядра (проверено на IEK и Systeme Electric из одной кодовой базы).
- **Развитие:** регулярное чтение данных учётной системы, лимиты бюджета, автоформирование черновика письма поставщику, графики трендов по категориям.

## 8. Учётные данные и публичный каталог

Для демонстрации установленная 1С не требуется. Реализовано чтение готовых файлов, без прямого коннектора и обратной записи заказа. Для эксплуатации нужен согласованный канал свежих данных: [ИНТЕГРАЦИЯ_1С.md](ИНТЕГРАЦИЯ_1С.md).

Каталог ekt.kz добавляет товарные категории и характеристики в отдельный локальный справочник. Внутренние категории и все расчётные значения сохраняют учётное происхождение; во время расчёта сеть не используется для каталога. См. [КАТАЛОГ_EKT.md](КАТАЛОГ_EKT.md).

## 9. Практическое развитие: качество данных, затем регионы

Работа из ветки `alish` использована как отдельная подготовка данных IEK для исследования качества и будущего обучения. Она не добавляет новую первичную историю и не заменяет рабочий алгоритм заказа. Сначала необходимо согласовать смысл пустых продаж, устранить расхождения между отчётами и измерить качество на последовательных исторических периодах; см. [АУДИТ_ВЕТКИ_ALISH.md](АУДИТ_ВЕТКИ_ALISH.md).

Девять городов на сайте — основание для планирования регионального охвата. В текущих учётных данных есть только Алматы; восемь других городов требуют собственных складских идентификаторов, продаж, запасов, резервов, ETA и сроков поставки. Перенос алматинского спроса на другие города создавал бы неподтверждённые заказы. Контракт подключения и состояние регионов — [ГОРОДА_И_СКЛАДЫ.md](ГОРОДА_И_СКЛАДЫ.md).

## Текущая поставка внутреннего сервиса

К бизнес-расчёту добавлены личные аккаунты manager/admin, постоянные заказы,
серверное сохранение количеств/утверждений, ревизии, журнал, очередь и Excel
сохранённой версии. Сотрудник сам утверждает позиции; отдельного согласования
руководителем в интерфейсе нет. Linux-развёртывание использует nginx с HTTPS,
systemd, один API и один worker, SQLite WAL и ежедневные резервные копии.
Подробности — [АРХИТЕКТУРА.md](АРХИТЕКТУРА.md), [DEPLOY.md](DEPLOY.md).

Каталог ekt.kz добавляет отдельную товарную классификацию и проверяемые
описания с частичным покрытием. Исследовательские CSV уже включены в поставку,
но не подключают ML-модель или новые склады. Числовые ограничения и критерии
приёмки остаются явно видимыми: [ПРИЕМКА.md](ПРИЕМКА.md).
