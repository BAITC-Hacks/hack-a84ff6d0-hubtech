# Архитектура сервиса автозаказов поставщикам (кейс ЭКТ)

> Как система устроена и как должна выглядеть: слои, потоки данных, модель Dataset, sequence расчёта, деплой.

---

## 1. Принцип решения

Менеджер закупа считает потребность вручную в Excel — редко и неточно, из-за чего возникают избыток по одним позициям и дефицит по другим. Сервис автоматизирует расчёт: читает реальные выгрузки 1С, строит прогноз спроса с сезонностью и трендом, компенсирует упущенный спрос, исключает разовый опт и формирует **рекомендованный заказ по каждому поставщику** с обоснованием. Итоговое решение остаётся за человеком — заказ утверждается вручную.

Ключевой архитектурный выбор: **месячные итоги 1С — источник истины по количеству**, транзакции служат для выявления исключительных (оптовых) заказов. Все окна прогноза и ETA — полуоткрытые `[as_of, as_of + H)`, единые по всему расчёту.

**Границы слоёв:** движок работает только с `Dataset` и не знает про источник — подключить новую выгрузку 1С можно, реализовав новый `DataSource`, без изменения ядра.

## 3. Технологический стек

| Слой | Технологии |
|---|---|
| Данные / ETL | Python, **pandas**, **openpyxl** (read-only, `data_only`) |

| Фронтенд | **React 19**, **Vite**, нативный fetch |
| Тесты | **pytest** (импорт, расчёт, экспорт), **vitest**-подобные unit на orderUtils |

## 5. Модель данных (Dataset)

Единый контейнер `app/data/adapter.py::Dataset` — набор DataFrame'ов:

```mermaid
erDiagram
    CATALOG ||--o{ SALES : "sku"
    CATALOG ||--o{ MONTHLY_SALES : "sku"
    CATALOG ||--o{ MONTHLY_STOCK : "sku"
    CATALOG ||--o{ STOCK : "sku"
    CATALOG ||--o{ IN_TRANSIT : "sku"
    CATALOG }o--|| SKU_SUPPLIERS : "sku→supplier"
    SUPPLIERS ||--o{ SKU_SUPPLIERS : "supplier_id"
    SUPPLIERS ||--o{ SEASONALITY : "supplier_id"

    CATALOG {
        string sku PK "код 1С"
        string name
        string category
        string unit
        string supplier_id
    }
    SALES {
        date date
        string sku
        float qty
        string warehouse
        string order_id
    }
    MONTHLY_SALES {
        string sku
        date month
        float qty
        float raw_qty
    }
    MONTHLY_STOCK {
        string sku
        date month
        float on_hand
        float raw_qty
    }
    STOCK {
        string sku
        string warehouse
        float on_hand
        date as_of
        string source
    }
    IN_TRANSIT {
        string sku
        float qty
        date eta
        date source_as_of
    }
    SUPPLIERS {
        string supplier_id PK
        int lead_time_days
        int min_order_qty
    }
    SKU_SUPPLIERS {
        string sku FK
        int pack_size
        int min_order_qty
        bool constraint_known
    }
    SEASONALITY {
        string supplier_id
        int month
        float factor
    }
```

Дополнительно `Dataset` несёт `as_of` (дата расчёта), `source` (`excel`/`csv`/`synthetic`), `warnings` (допущения для UI) и `metadata` (счётчики качества данных).

## 6. Ролевая модель

Кейс однопользовательский на MVP: основной пользователь — **менеджер отдела закупа**. Разграничение доступа/аутентификация в MVP не реализованы (см. НФТ и Roadmap). Целевая роль руководителя (утверждение крупных заказов) описана в [КОНЦЕПЦИЯ_СИСТЕМЫ_РК.md](КОНЦЕПЦИЯ_СИСТЕМЫ_РК.md).

## 7. Сценарий «расчёт заказа» (последовательность)

```mermaid
sequenceDiagram
    actor M as Менеджер закупа
    participant UI as React
    participant API as FastAPI
    participant ENG as Движок
    participant LLM as OpenAI/Codex
    M->>UI: выбрать склад/категорию, «Рассчитать»
    UI->>API: POST /api/recommend
    API->>ENG: generate_recommendations(ds, фильтры)
    ENG->>ENG: по SKU: опт→stockout→прогноз→потребность
    ENG->>LLM: обоснование строки (если explain=true)
    LLM-->>ENG: текст (или шаблон при сбое/без ключа)
    ENG-->>API: RecommendationResponse
    API->>API: save_snapshot(calculation_id)
    API-->>UI: заказы по поставщикам + calculation_id
    M->>UI: корректировка кол-ва, утверждение
    UI->>API: POST /api/recommend/export {calculation_id, approved_only}
    API-->>UI: Excel (approved_order.xlsx)
```

## 10. Нефункциональные требования

| НФТ | Как обеспечено |
|---|---|
| **Приватность** | Клиентские данные обезличены; в выгрузках 1С клиентов нет — опт выявляется по транзакциям |
| **Объяснимость** | Раскладка расчёта + обоснование по каждой строке; 15 предупреждений о допущениях |
| **Устойчивость к выбросам** | Robust-детекция (Тьюки/медиана), клиппинг отрицательных, сверка транзакций с месяцами |
| **Совместимость с 1С** | Экспорт в Excel; чтение стандартных выгрузок без изменения учётной системы |
| **Безопасность решений** | Заказ не отправляется автоматически — только рекомендация + ручное утверждение |
| **Воспроизводимость** | Кеш импорта по fingerprint файлов; детерминированная синтетика (seed) |
| **Производительность** | Полный расчёт ~26с на 250k транзакций (батч); группировка один раз, без квадратичного скана |
