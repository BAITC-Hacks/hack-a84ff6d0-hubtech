# Бэкенд: реализованный сервис и границы production-ТЗ

Актуально после интеграции `baitc/frontend` (`5a0ace2`) и исправлений расчёта. В API теперь есть именные пользователи, сохранённые заказы, история действий, проверка версии, очередь и отдельный worker. **Это не реализация всех пяти ролей и независимого согласования из [ТЗ платформы](ТЗ_платформы.md).** Ниже приведён фактический контракт; будущие функции обозначены отдельно.

## 1. Стек и модули

Поддерживаемый runtime — Python 3.12. FastAPI/uvicorn, Pydantic v2, pandas/numpy/scipy, openpyxl, Argon2id, SQLite WAL. `statsmodels` установлен, но текущий прогноз не вызывает его. Прямые зависимости закреплены в `backend/requirements.txt`, прямые и транзитивные — в `backend/requirements.lock`; тестовые — `requirements-dev.txt`. BeautifulSoup используется только отдельной синхронизацией EKT.

| Модуль | Ответственность |
|---|---|
| `main.py` | Миграции при старте, middleware, безопасные ошибки и журнал request ID |
| `api/routes.py`, `api/models.py`, `schemas.py` | HTTP-контракты, валидация и зависимости доступа |
| `security.py` | Пароли, сессии, CSRF, проверка origin, ограничение попыток входа |
| `storage.py` | SQLite, транзакции, внешние ключи, миграции |
| `repositories.py` | Пользователи, принадлежность заказов, решения, revision, события и экспорт |
| `jobs.py`, `worker.py` | Постоянная очередь, идемпотентность, выполнение и отмена в дочернем процессе |
| `manage.py`, `ops.py` | Создание администратора, миграции, online-копии и offline-восстановление |
| `data/` | Excel/CSV/synthetic → `Dataset`, дополнительный локальный справочник EKT |
| `core/` | Расчёт, объяснение и Excel |

## 2. Доступ и сохранение

- Две роли: `manager` работает со своими заказами; `admin` управляет сотрудниками и имеет доступ ко всем заказам. Области доступа по отдельным складам/поставщикам отсутствуют.
- Первый администратор создаётся CLI со скрытым вводом пароля; открытой регистрации и стандартного пароля нет. Администратор создаёт остальных сотрудников через API/UI. Последнего активного администратора нельзя отключить или понизить.
- Пароли хешируются Argon2id. Сессия живёт восемь часов; в БД хранится SHA-256 непрозрачного session token. Cookie — `HttpOnly`, `SameSite=Strict`, в production также `Secure`.
- Изменяющие запросы требуют `X-CSRF-Token`. При наличии заголовка `Origin` он должен совпасть с `APP_ORIGIN` либо origin API. CORS по умолчанию отключён; wildcard запрещён.
- Смена роли/пароля и отключение аккаунта отзывают его сессии. Отключение также отменяет незавершённые задания. Ограничение входа: пять попыток на имя пользователя или двадцать на IP за 15 минут; успешный вход очищает счётчик этого имени.
- Путь SQLite: `APP_DB_PATH`, затем совместимый `ORDER_DB_PATH`, затем `backend/.cache/orders.sqlite3`. База должна быть на локальном диске. Короткие транзакции используют WAL, foreign keys и busy timeout.
- Исходный расчёт сохраняется неизменяемым JSON. Текущие количества и флаги строк находятся отдельно. У заказа есть владелец, заголовок, `revision`, архивный признак и даты; сохранённые заказы не удаляются по лимиту 50/7 суток.
- События хранят исполнителя, время и изменения «до/после». Это журнал действий, а не отдельные неизменяемые снимки каждой исторической версии решений.
- Унаследованные снимки импортируются в архив первого администратора однократно, без выдуманных подтверждений и истории. Старый `snapshots.py` остаётся для совместимости; его очистка не удаляет постоянные заказы.

`approved` сейчас означает **подтверждение позиции самим пользователем с доступом к заказу**. Другого согласующего и этапов `submitted/approved/changes_requested` нет. Нельзя описывать этот флаг как независимое согласование руководителем.

## 3. HTTP API

Базовый префикс `/api`. Все операции, кроме login/health/ready, требуют входа; изменяющие операции после входа дополнительно требуют CSRF.

| Метод | Путь | Реализованное поведение |
|---|---|---|
| GET | `/health` | Живость процесса; не проверяет качество данных |
| GET | `/ready` | 200/503: БД доступна, heartbeat worker свежий, обязательные исходные файлы доступны и не пусты |
| POST | `/auth/login` | `{username,password}` → cookie и `{user,csrf_token}` |
| GET | `/auth/session` | Пользователь и CSRF-токен действующей сессии |
| POST | `/auth/logout` | Удаление сессии и cookie |
| GET/POST | `/users` | Список/создание сотрудников, только admin |
| PATCH | `/users/{id}` | `{role?,active?,password?}`, только admin |
| GET | `/meta` | Склады, категории, поставщики, даты, качество, defaults/capabilities, товарные группы EKT |
| POST | `/recommend` | Задание; `Prefer: respond-async` возвращает `202 {job_id,status}` |
| GET | `/jobs` | Доступные задания, до 100 последних |
| GET | `/jobs/{id}` | `id,status,created_at,updated_at,order_id,error` |
| POST | `/jobs/{id}/cancel` | Отмена queued/running-задания |
| GET | `/orders` | `{items,total}`, параметры `limit` (1–100), `offset`, `archived` |
| GET | `/orders/{id}` | Метаданные, `calculation`, текущие `decisions`, revision |
| PUT | `/orders/{id}` | `{revision,lines}` — сохранение полного набора решений |
| PATCH | `/orders/{id}` | `{revision,title?,archived?}` |
| GET | `/orders/{id}/events` | Журнал изменений и скачиваний доступного заказа |
| POST | `/orders/{id}/export` | `{revision,approved_only}` → XLSX сохранённой версии |
| POST | `/recommend/export` | Legacy-совместимость: экспорт только при точном совпадении переданных и сохранённых решений |

`RecommendRequest`: `warehouse?`, внутренняя `category?`, `product_category?` EKT, `service_level?` (0.5–0.999), `review_period_days?` (1–120), `explain=false`. Неизвестные поля, строковые числовые значения и логическое значение вместо числа отклоняются. Разные товарные классификации не подменяют друг друга.

Без `Prefer: respond-async` endpoint ждёт **то же** постоянное задание: при завершении отдаёт `RecommendationResponse`, при превышении времени ожидания — 202 с ID задания. Новый UI использует асинхронный контракт.

`Idempotency-Key` относится к владельцу и параметрам расчёта: повтор возвращает прежнее задание, изменение параметров с тем же ключом даёт 409. Новый ключ означает новую попытку. Для PUT/PATCH заказа используется revision; отдельной идемпотентности этих команд и экспортных событий нет.

| Код | Значение |
|---|---|
| 401 | Нет действующей сессии / аккаунт отключён |
| 403 | Нет прав на объект, неверный CSRF или origin |
| 404 | Объект не найден |
| 409 | Устаревшая revision, несовместимый повтор, активный расчёт либо несохранённый legacy-экспорт |
| 410 | Не найден расчёт для legacy-экспорта |
| 422 | Невалидная команда, количество, состав, единица или пустой экспорт |
| 429 | Лимит входа либо заполненная очередь |
| 503 | Worker недоступен / readiness не пройдена |

## 4. Сохранение и Excel

Сервер требует полный набор `{line_id,quantity,approved}` исходного расчёта: чужие, пропущенные и повторные строки отклоняются. Проверяются конечное неотрицательное число, MOQ, кратность и невозможность подтвердить нулевое количество. Неизвестная единица (`ед. (не указана)` или пустая строка) не допускает подтверждения положительной позиции; её можно сохранить и показать в черновике с ограничениями данных.

Изменение количества атомарно снимает подтверждение, даже если клиент одновременно прислал `approved=true`. Нужно сначала сохранить число, затем подтвердить строку. Чужая или устаревшая revision возвращает 409 без частичного сохранения. Архивный заказ нужно восстановить перед редактированием.

Штатный экспорт читает сохранённый расчёт и решения, сверяет revision до формирования и перед записью события скачивания. Он не читает источники и не вызывает прогноз. В файле есть коды 1С/поставщика, склад, единица, рекомендация, выбранное количество, флаг подтверждения, ограничения, поля EKT, ID расчёта, **ID/версия/владелец/название заказа и дата сохранения**. Текст из источника остаётся текстом, включая значения с `=`.

Legacy `/recommend/export` больше не позволяет передать несохранённые количества или подтверждения в обход истории: корректные, но отличающиеся решения дают 409. Клиент должен сохранить заказ и скачать его текущую версию. Экспорт не отправляет поставщику заказ и не создаёт документ 1С; совместимость с целевой конфигурацией 1С проверяется отдельно.

## 5. Очередь и ограничение работы

`python -m app.worker` — один supervisor с SQLite lease и heartbeat. Он последовательно запускает по одному расчёту в отдельном дочернем процессе. Статусы: `queued → running → completed/failed/cancelled`. `completed` — фактическое имя статуса API, не `succeeded` из целевого ТЗ.

По умолчанию очередь ограничена 20 queued/running-заданиями, у одного пользователя допускается только одно активное. Без свежего worker новое задание не принимается. Отмена и таймаут 600 секунд завершают дочерний процесс; условная запись результата запрещает позднему/отменённому заданию создать заказ. После потери lease или перезапуска running-задания отмечаются ошибкой, queued сохраняются; неуспешный расчёт требует нового явного запуска.

Внешние объяснения выключены по умолчанию на уровне запроса. При явном `explain=true` и наличии ключа OpenAI передаются название товара, количество, срочность и `Rationale` с коммерческими показателями. Timeout одного обращения не более десяти секунд, retries=0, общий бюджет объяснений 120 секунд. Ошибка/отсутствие ключа/исчерпание бюджета возвращают локальный шаблон и не меняют количество. Права на включение провайдера по пяти целевым ролям пока отсутствуют; настройка ключа сама по себе не заменяет политику компании.

## 6. Расчёт и входные данные

- `outliers.py`: объединение результатов детекции по клиенту/дню и документу/дню в пределах SKU×склад. Не менее пяти положительных наблюдений, одновременно `> Q3 + 3·IQR` и `≥ 8 × median`. Документы не скрывают крупную покупку клиента; каждая строка исключается один раз. Неизвестные клиенты не объединяются в одного покупателя.
- `stockout.py`: дневная компенсация по здоровым дням и **месячная компенсация по явно переданным интервалам**. Частичное отсутствие оценивается по доступным дням; согласованные транзакции позволяют учесть продажи во время отсутствия. Полностью недоступный месяц использует медиану до трёх предыдущих пригодных месяцев; без истории добавка не выдумывается. Метод и ограничения показаны в предупреждениях. В текущих реальных Excel интервалы stockout отсутствуют.
- `forecasting.py`: дневной и месячный прогнозы с сезонностью и ограниченным линейным трендом. Из месячных итогов не генерируются наблюдённые дневные продажи.
- `replenishment.py`: `прогноз(H) + z·σ·√H − остаток − путь`, где `H = lead time + review period`; затем MOQ и кратность. Для ETA и прогноза применяется единое полуоткрытое окно; поздние/неподтверждённые приходы не уменьшают заказ.
- `recommend.py`: месячные количества — текущий выбранный источник объёма, транзакции — источник детекции опта. Несогласованные месячные объёмы не уменьшаются на найденный опт без сверки.

Источники: `excel` (12 файлов IEK/Systeme), `csv` (шесть файлов контракта) и `synthetic`. Excel читается read-only по сохранённым значениям формул. Кеш по path/mtime/size защищён от параллельного холодного импорта; каждый потребитель получает копии DataFrame. Это не полноценное версионирование входных партий.

EKT читается из локального JSON, без сети в расчёте. Сохраняются категория 1С, отдельная товарная группа, точное сопоставление и карантин конфликтов. `/meta` и сохранённый расчёт возвращают безопасные счётчики/дату/источник `catalog_enrichment`, без серверных путей. Список складов — объединение `sales/monthly_sales/stock/in_transit`; девять городов сайта не превращаются в учётные склады.

## 7. Что остаётся по полному ТЗ

Реализованы вход, owner-доступ, постоянные решения, optimistic revision, очередь, аудит и резервные копии SQLite. Предстоят пять бизнес-ролей и области склада/поставщика, запрет самоутверждения, независимое согласование, сохранённые исторические версии решений, один поставщик на заказ, подтверждаемые партии импорта, формальная политика свежести и рабочей/исторической выгрузки, PostgreSQL/версионированные исходники, управленческий обзор и подтверждённые нагрузочные/SLA/RPO/RTO показатели.

Текущий заказ может включать несколько групп поставщиков; архивирование не означает завершение согласования. Readiness проверяет доступность файлов, **не их семантическую полноту, свежесть или корректность каждой строки**. Эти различия нельзя скрывать под названием production.
