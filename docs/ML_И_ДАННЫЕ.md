# Прогнозирование и учётные данные

Движок формирует объяснимую оценку пополнения по доступным выгрузкам. Числа рассчитывают pandas/numpy/scipy; OpenAI API может только переформулировать обоснование. Обучаемой модели LightGBM или Holt в текущем прогнозе нет. Для существующей функции месячного прогноза выполнена последовательная временная оценка на реальных Excel; общее преимущество над простым базовым методом не подтверждено. [Протокол backtest](../scripts/BACKTEST.md) и раздел 9 описывают результат и его границы.

## 1. Источники и их роли

По каждому поставщику в `IEK/` и `Systeme electric/` предоставлено шесть Excel-файлов.

| Источник | Роль |
|---|---|
| Транзакции продаж | Дата, SKU, склад, количество, номер документа; поиск крупных заказов и дневной прогноз при отсутствии месячной истории |
| Месячные продажи | Основной источник объёма, когда доступен; используются только завершённые месяцы |
| Месячные остатки | Последний известный начальный баланс месяца как датированный устаревший снимок |
| MOQ / кратность | Ограничения заказа по артикулу |
| Товары в пути | Количества и ETA; для части Systeme также свободный остаток на дату снимка |
| Сезонность | 12 коэффициентов по каждому поставщику |

Выбор месячных итогов основным источником — договорённость текущего алгоритма до сверки с партнёром, а не доказательство большей точности этих отчётов. При расхождении объёмов исходная месячная сумма сохраняется.

Каталог ekt.kz добавляет только описательные поля и товарные фильтры. Он не используется для восстановления ежедневных продаж, остатков или закупочных условий: [КАТАЛОГ_EKT.md](КАТАЛОГ_EKT.md). Контракт учётных данных и пробелы — в [ИНТЕГРАЦИЯ_1С.md](ИНТЕГРАЦИЯ_1С.md).

## 2. ETL и ограничения

Импорт выполняет `backend/app/data/excel.py`: `openpyxl` читает файл без записи, формулы — по сохранённым значениям, внешние ссылки не обновляются. `reset_dimensions()` позволяет читать листы с устаревшими сведениями о размере. Каталог собирается по строковому коду 1С с сохранением значимых нулей и подчёркиваний.

- Пустые ячейки месячных продаж трактуются как нули разреженной выгрузки. Пустой остаток означает неизвестное значение.
- Отрицательные транзакции исключены из положительного спроса как возвраты/корректировки. Отрицательный месячный итог ограничен нулём, исходное значение сохраняется в `raw_qty`.
- Остаток берётся из датированного свободного остатка, где он доступен, иначе из последнего месячного снимка. Движения после старого снимка не восстанавливаются. Неизвестная часть остатка принимается за ноль для предварительной оценки и отмечается предупреждением.
- Клиентских идентификаторов и цен сделок в приложенных выгрузках нет. Номер документа позволяет объединить его строки, но не заменяет клиента.
- Точные периоды отсутствия не получены. Из месячных остатков ежедневные stockout-интервалы не выводятся.
- Сводные месячные данные и путь отнесены к Алматы по области выгрузок. Сроки новых заказов IEK 21 день / Systeme 35 дней — неподтверждённые настройки.
- Коэффициент сезонности поставщика применяется к его SKU как приближение, а не как измеренная сезонность каждого товара.

Зафиксированный набор: 3 907 SKU, 248 467 положительных транзакций, 99 561 строка месячных продаж и 84 471 строка месячных остатков. Фактические даты, объёмы и предупреждения возвращаются в `/api/meta`; количество предупреждений не фиксируется константой.

## 3. Крупные заказы

`outliers.py` независимо проверяет два уровня: настоящий документ + календарный день и обезличенный клиент + календарный день. Наличие номера документа не отменяет клиентскую проверку: покупка одного клиента, разбитая на десять документов в один день, остаётся одним клиентским событием. Порог определяется отдельно внутри `(sku, warehouse)` и каждого уровня. Отсутствующие идентификаторы оставляют строки отдельными наблюдениями, а не объединяют их в одного «неизвестного клиента».

Для детекции требуется минимум **пять положительных наблюдений на соответствующем уровне**. Десять документов одного клиентского дня не превращаются в десять клиентских дней. Кандидат должен одновременно превышать `Q3 + 3 × IQR` и составлять не менее восьми медиан. Результат — объединение отмеченных положительных строк: каждая строка вычитается один раз. При совпадении документной и клиентской детекции счётчик/обоснование используют клиентское событие. Возвраты не классифицируются как положительный опт. Единственная продажа не удаляется только из-за своей доли.

В месячном режиме сумма исходных положительных транзакций сначала сверяется с итогом того же SKU/склада/месяца. Только при численном совпадении найденный крупный объём вычитается из месячного итога, не более этого итога. При расхождении крупный объём не вычитается, выдаётся предупреждение. Счётчики сверки: `data_quality.calculation_reconciliation`.

## 4. Восстановление stockout

`stockout.py` применяется **в дневной и месячной ветках** только к явно переданным включительным интервалам данного SKU и склада. Пересечения интервалов считаются один раз. Для дневной ветки продажи со временем суммируются по календарному дню. Ожидаемый спрос оценивается по доступным дням той же недели и, при достаточном числе наблюдений, того же месяца.

Наблюдавшийся спрос не уменьшается: используется максимум факта и оценки. `lost_demand_uplift` — только добавленная разница, не всё замещённое значение. Выходные учитываются через собственный день недели.

В месячной ветке корректируется **месячный объём после исключения опта**, без создания вымышленных дневных продаж. Учитываются только завершённые месяцы до последнего подтверждённого дня источника.

Для частичного отсутствия `D` — число дней месяца, `O` — уникальные дни отсутствия, `A = D − O` — доступные календарные дни, `Q` — регулярный месячный объём. Если исходный месяц численно согласован с транзакциями, `Qout` берётся из регулярных продаж, фактически наблюдавшихся внутри интервалов; иначе `Qout = 0` — явно показанное в предупреждении допущение, что месячные продажи пришлись на доступные дни.

```text
rate = max(0, Q − Qout) / A
uplift = max(0, rate × O − Qout)
adjusted_month = Q + uplift
```

При полном отсутствии (`A = 0`) используется медиана наблюдённого доступного среднесуточного спроса **до трёх предыдущих месяцев с доступными днями**. Более поздние месяцы и уже восстановленные полные месяцы не участвуют в этой оценке. Добавляется только положительная разница между оценкой полного месяца и фактом. Если предшествующей опоры нет, компенсация равна нулю и возвращается предупреждение о невозможности её оценить. Это приближение не доказывает сезонный спрос в полностью отсутствующем месяце; оно явно обозначается в обосновании.

Регрессионный пример: в мае продажи по 10 единиц в каждый из 11 доступных дней, отсутствие 1–20 мая. Месячная коррекция добавляет **200**, а заказ на семидневный горизонт меняется **40 → 70**. Дневная ветка на том же наборе добавляет те же 200. Отдельно проверяются продажи внутри интервалов, полное отсутствие, пересечения, разные склады и запрет будущих данных.

В приложенных реальных Excel точных интервалов по-прежнему нет: их отсутствие не восполняется из месячных остатков, поэтому на этом наборе uplift равен нулю. Исправленная возможность и наличие достаточных рабочих данных — разные условия.

## 5. Дневной и месячный прогноз

| Компонент | Дневные наблюдения | Месячные итоги |
|---|---|---|
| История | До последнего завершённого подтверждённого дня | Только завершённые месяцы; текущий неполный месяц исключён |
| Уровень | Среднее десезонализированного ряда за последние 90 дней | Среднее десезонализированных среднесуточных значений последних 3 месяцев |
| Тренд | Линейный наклон недельных средних на последних 180 днях | Линейный наклон среднесуточных значений последних 6 месяцев |
| Временная шкала | Реальные расстояния между днями; недельные точки привязаны к средним датам | Точки привязаны к серединам фактических месяцев |
| σ для страхового запаса | Наблюдаемое стандартное отклонение последних 90 дней, включая нули | Оценка: максимум `sqrt(прогноз_день)` и разброса месячных среднесуточных значений |

Месячный итог делится на число дней месяца для оценки скорости спроса. Он не распределяется на вымышленные ежедневные продажи. Дневная вариативность в этом режиме неизвестна, поэтому приближение Пуассона и межмесячный разброс явно отмечены в предупреждениях.

Перед оценкой тренда ряд десезонализируется. При наличии таблицы поставщика её коэффициенты нормируются к среднему уровню 1. При отсутствии внешних коэффициентов достаточно длинная история позволяет оценить месячные отношения; короткая история использует нейтральную сезонность. При недостаточном количестве точек наклон равен нулю.

Прогноз вычисляется по дням горизонта: линейно спроецированный уровень ограничивается снизу нулём, умножается на сезонность соответствующего месяца, затем усредняется. `seasonality_factor` и `trend_factor` помогают объяснить результат; их произведение с уровнем не обязано в точности совпадать со средним дневных произведений на границе сезонов.

## 6. Горизонт, потребность и срочность

```text
H = срок нового заказа + период проверки
окно = [as_of, as_of + H)
спрос(H) = средний прогноз в день × H
страховой запас = z(уровень сервиса) × σ × √H
потребность = спрос(H) + страховой запас − остаток − допустимые приходы
заказ = округление вверх max(положительная потребность, MOQ) до кратности
```

MOQ применяется **перед** округлением; MOQ артикула приоритетнее общего условия поставщика. Кратность может быть дробной.

Из потребности вычитаются только приходы с ETA в том же окне. Просроченные, неизвестные, слишком поздние ETA и снимки из будущего относительно исторической даты расчёта не считаются доступным приходом. Их объём показан как `ignored_in_transit`.

Срочность проверяет первый дефицит по последовательности датированных приходов. Наличие большого позднего поступления не скрывает отсутствие товара до его даты. Если суммарного объёма достаточно, но до прихода будет дефицит, строка имеет нулевой дополнительный заказ и рекомендацию ускорить поставку или переместить запас.

## 7. Обоснование и проверки

Каждая строка содержит `Rationale`, предупреждения и текст с фактической единицей товара. Обоснование по умолчанию строится шаблоном; при `explain=true` и ключе используется OpenAI API. LLM не выбирает количество и не заменяет расчёт.

После интеграции `baitc/frontend` (`5a0ace2`) эти числовые правила применяются и в отдельном worker сервиса. Заказы и правки сохраняются в SQLite; это не меняет методику прогноза и не превращает сохранённую отметку строки в независимое согласование руководителя. Контракт ролей и производства — [ТЗ_платформы.md](ТЗ_платформы.md). Для воспроизводимого запуска без файлов компании доступны synthetic с фиксированной датой 23.09.2026 и [CSV-пример](../data/sample_csv/README.md) с явными единицами.

```bash
cd backend
OPENAI_API_KEY='' ./.venv/bin/python -m unittest discover -s tests -v
OPENAI_API_KEY='' RUN_REAL_EXCEL_TESTS=1 ./.venv/bin/python -m unittest tests.test_excel_import -v
OPENAI_API_KEY='' ./.venv/bin/python -m tests.validate_must_have
OPENAI_API_KEY='' ./.venv/bin/python -m unittest tests.test_calculation tests.test_input_contract -v
```

`validate_must_have` проверяет пять групп **на небольших данных с фиксированными датами и точными ожидаемыми результатами**. MH1 использует 14 проверок: эталон, дневной/месячный объём, отсутствие двойного сложения источников, остаток, допустимый/поздний ETA, срок и связь поставщика, MOQ и кратность, категория как фильтр и запрет вывода дневного stockout из месячного остатка. MH2 сравнивает один набор с сезонностью и без неё (`70 → 140`) и известный линейный тренд (`203/день`); MH3 сравнивает заказ с интервалами и без них в обеих ветках; MH4 проверяет клиента с десятью документами; MH5 — два поставщика и обоснования каждой строки.

Регрессии дополнительно проверяют короткую историю, объединение детекций без двойного вычитания, месячную сверку, stockout и опт одновременно, даты/склады/ETA и экспорт. Это не измерение точности прогноза, достигнутого уровня сервиса, снижения запасов или официальный допуск по кейсу. Внешний коэффициент роста алгоритм не принимает: рост оценивается по истории; категория выбирает область, но не меняет количественную формулу.

## 8. Подготовка обучающей выборки IEK

В `scripts/` интегрирована проверенная подготовка из `baitc/alish` (`5facda2` и предшествующие коммиты скриптов). Новая вершина ветки `08a0ce0` обнаружена при обновлении ссылок, но не входит в этот аудит и не объявляется проверенной интеграцией. Это отдельный процесс исследования: `clean_monthly_data.py` сохраняет очищенную месячную таблицу и проблемы ячеек; `prepare_ml_data.py` строит панель, лаги и временные разбиения в `data/ml/iek/`. Сеть и подключение к 1С для него не нужны. Результаты не меняют текущую формулу заказа.

По умолчанию неизвестные месячные продажи сохраняются неизвестными, отрицательные значения остаются в raw-полях и исключаются из целей. При этой политике в проверенных данных 28 979 обучающих строк по 1 755 SKU, все цели положительны. В рабочем Excel-импорте другое допущение — пустая продажа равна нулю. Без согласованной семантики пустот оценка только по положительным месяцам не описывает качество на всём ассортименте.

Разбиения задаются общими датами: train до конца декабря 2025, validation январь–июнь 2026, test июль–август 2026. Признаки используют только прошлые месяцы; коэффициенты сезонности из текущего файла, нынешние MOQ и путь в исторические признаки не включены. Готовые CSV сами по себе не обеспечивают правильное обучение: код оценки должен переобучать модель на доступном прошлом и отдельно показывать покрытие SKU, месяцы с нулевым спросом и fallback при короткой истории.

Сентябрьская строка признаков — прогноз полного сентября из истории до августа. Она не является прогнозом остатка месяца с 23 сентября и не подменяет ежедневный горизонт заказа текущего движка. Обученная модель не добавлена; опубликованный отдельно backtest ниже проверяет действующую функцию прогноза, а не обучает модель на `training_data.csv`.

Подробные результаты, исправления и назначение каждого файла — [АУДИТ_ВЕТКИ_ALISH.md](АУДИТ_ВЕТКИ_ALISH.md); команды и контракт — [ML_PREPARATION.md](../scripts/ML_PREPARATION.md). Склады и ограничения региональной истории — [ГОРОДА_И_СКЛАДЫ.md](ГОРОДА_И_СКЛАДЫ.md).

## 9. Измеренная временная проверка текущего прогноза

[`scripts/backtest_forecast.py`](../scripts/backtest_forecast.py) проверяет `forecast_monthly_demand` на **3 017 SKU месячных продаж**: 2 463 IEK и 554 Systeme Electric. Это область месячных отчётов, а не все 3 907 SKU объединённого рабочего каталога. Семь IEK SKU без известной единицы отражены в покрытии, но исключены из количественных метрик.

Протокол — rolling-origin, то есть последовательный прогноз каждого полного месяца из доступного до него прошлого. **Validation: январь–июнь 2026; test: июль–август 2026.** Для августа разрешён уже завершённый июль. Сентябрь не оценивается как полный месяц. В прогноз не передаются будущие месяцы, текущие внешние коэффициенты сезонности, остатки, MOQ, путь, транзакции или клиентские признаки. Историческая сезонность оценивается самой функцией только по прошлым месяцам; обучение ML и подбор параметров по test не выполняются.

Проверяются две политики: `unknown_blanks` сохраняет пропуски/отрицательные итоги неизвестными; `operational_zero_assumption` принимает пустую ячейку существующей строки и отрицательный итог за ноль. Последняя соответствует операционному допущению, которое должен подтвердить владелец данных. Явный ноль не отбрасывается. Неизвестный факт не становится нулём ради подсчёта метрик.

Сравнение проводится с `last_month` и `same_month_last_year`. Для вывода о качестве используются одинаковые строки (`paired_*` или `common_all_models`), отдельно по поставщику, политике, периоду и единице. `available` показывает охват каждого метода, но не даёт честного сравнения при разном составе строк. Рассчитываются MAE, WAPE, bias, ошибка на нулевых целях и покрытие; при нулевой сумме факта WAPE/bias не определены. Метры, штуки, упаковки и комплекты не складываются в общий объёмный показатель ошибки.

На test июля–августа, `operational_zero_assumption`, `common_all_models`, WAPE:

| Поставщик / единица | Текущий прогноз | Предыдущий месяц | Тот же месяц год назад |
|---|---:|---:|---:|
| IEK / шт | 39,23% | 34,65% | 43,93% |
| IEK / м | 62,53% | 72,60% | 94,70% |
| IEK / упак | 42,90% | 29,64% | 32,24% |
| Systeme Electric / шт | 25,47% | 18,58% | 36,29% |

Меньше — лучше. Текущий метод проигрывает предыдущему месяцу в штуках и упаковках и выигрывает в метрах на этом срезе. **Общее преимущество по ассортименту не доказано**, алгоритм не заменён ради удачного числа. При консервативной политике охват существенно меньше; результаты нельзя переносить между политиками как улучшение модели.

Это оценка функции месячного прогноза, **не всего заказа** с оптом, stockout, страховым запасом и поставками. Ретроспективные Excel могут содержать поздние исправления, исторических снимков на каждую дату нет. Источники могли изучаться при разработке; оценка не является слепым перспективным испытанием. После просмотра test дальнейшие изменения должны явно отмечать его повторное использование и проверяться на новом будущем периоде. Из этих двух тестовых месяцев нельзя выводить годовую точность, экономию или готовность к production.
