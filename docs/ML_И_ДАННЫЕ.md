# Прогнозирование и учётные данные

Движок формирует объяснимую оценку пополнения по доступным выгрузкам. Числа рассчитывают pandas/numpy/scipy; OpenAI API может только переформулировать обоснование. Обучаемой модели LightGBM или Holt в текущем прогнозе нет. Точность на отложенном периоде пока не измерялась.

## 1. Источники и их роли

По каждому поставщику в `IEK/` и `Systeme electric/` предоставлено шесть Excel-файлов.

| Источник | Роль |
|---|---|
| Транзакции продаж | Дата, SKU, склад, количество, номер документа; поиск крупных заказов и дневной прогноз при отсутствии месячной истории |
| Месячные продажи | Основной источник объёма, когда доступен; используются только завершённые месяцы |
| Месячные остатки | Последний известный начальный баланс месяца как датированный устаревший снимок |
| MOQ / кратность | Ограничения заказа по артикулу |
| Товары в пути | Количества и ETA; для части Systeme также свободный остаток на дату снимка |
| Сезонность | 12 коэффициентов по каждому поставщику |

Выбор месячных итогов основным источником — договорённость текущего алгоритма до сверки с партнёром, а не доказательство большей точности этих отчётов. При расхождении объёмов исходная месячная сумма сохраняется.

Каталог ekt.kz добавляет только описательные поля и товарные фильтры. Он не используется для восстановления ежедневных продаж, остатков или закупочных условий: [КАТАЛОГ_EKT.md](КАТАЛОГ_EKT.md). Контракт учётных данных и пробелы — в [ИНТЕГРАЦИЯ_1С.md](ИНТЕГРАЦИЯ_1С.md).

## 2. ETL и ограничения

Импорт выполняет `backend/app/data/excel.py`: `openpyxl` читает файл без записи, формулы — по сохранённым значениям, внешние ссылки не обновляются. `reset_dimensions()` позволяет читать листы с устаревшими сведениями о размере. Каталог собирается по строковому коду 1С с сохранением значимых нулей и подчёркиваний.

- Пустые ячейки месячных продаж трактуются как нули разреженной выгрузки. Пустой остаток означает неизвестное значение.
- Отрицательные транзакции исключены из положительного спроса как возвраты/корректировки. Отрицательный месячный итог ограничен нулём, исходное значение сохраняется в `raw_qty`.
- Остаток берётся из датированного свободного остатка, где он доступен, иначе из последнего месячного снимка. Движения после старого снимка не восстанавливаются. Неизвестная часть остатка принимается за ноль для предварительной оценки и отмечается предупреждением.
- Клиентских идентификаторов и цен сделок в приложенных выгрузках нет. Номер документа позволяет объединить его строки, но не заменяет клиента.
- Точные периоды отсутствия не получены. Из месячных остатков ежедневные stockout-интервалы не выводятся.
- Сводные месячные данные и путь отнесены к Алматы по области выгрузок. Сроки новых заказов IEK 21 день / Systeme 35 дней — неподтверждённые настройки.
- Коэффициент сезонности поставщика применяется к его SKU как приближение, а не как измеренная сезонность каждого товара.

Зафиксированный набор: 3 907 SKU, 248 467 положительных транзакций, 99 561 строка месячных продаж и 84 471 строка месячных остатков. Фактические даты, объёмы и предупреждения возвращаются в `/api/meta`; количество предупреждений не фиксируется константой.

## 3. Крупные заказы

`outliers.py` группирует строки по настоящему номеру документа; при его отсутствии — по обезличенному клиенту и календарному дню, иначе оставляет отдельные наблюдения. Группировка выполняется уже внутри пары `(sku, warehouse)`.

Для детекции требуется минимум **пять положительных наблюдений**. Кандидат должен одновременно превышать `Q3 + 3 × IQR` и составлять не менее восьми медиан. Правила «исключать любую продажу больше 40% объёма» в текущей реализации нет. Единственная продажа не удаляется как опт только из-за своей доли.

В месячном режиме сумма исходных положительных транзакций сначала сверяется с итогом того же SKU/склада/месяца. Только при численном совпадении найденный крупный объём вычитается из месячного итога, не более этого итога. При расхождении крупный объём не вычитается, выдаётся предупреждение. Счётчики сверки: `data_quality.calculation_reconciliation`.

## 4. Восстановление stockout

`stockout.py` применяется **в дневной ветке** и только к явно переданным интервалам данного SKU и склада. Продажи со временем суммируются по календарному дню. Ожидаемый спрос оценивается по здоровым дням той же недели и, при достаточном числе наблюдений, того же месяца.

Наблюдавшийся спрос не уменьшается: используется максимум факта и оценки. `lost_demand_uplift` — только добавленная разница, не всё замещённое значение. Выходные учитываются через собственный день недели.

В текущей месячной ветке stockout-коррекция не применяется. Даже получение явных интервалов для товара с месячной историей потребует отдельного расширения этого пути. На приложенных реальных данных uplift не подтверждён; механизм проверяется на дневных синтетических сценариях.

## 5. Дневной и месячный прогноз

| Компонент | Дневные наблюдения | Месячные итоги |
|---|---|---|
| История | До последнего завершённого подтверждённого дня | Только завершённые месяцы; текущий неполный месяц исключён |
| Уровень | Среднее десезонализированного ряда за последние 90 дней | Среднее десезонализированных среднесуточных значений последних 3 месяцев |
| Тренд | Линейный наклон недельных средних на последних 180 днях | Линейный наклон среднесуточных значений последних 6 месяцев |
| Временная шкала | Реальные расстояния между днями; недельные точки привязаны к средним датам | Точки привязаны к серединам фактических месяцев |
| σ для страхового запаса | Наблюдаемое стандартное отклонение последних 90 дней, включая нули | Оценка: максимум `sqrt(прогноз_день)` и разброса месячных среднесуточных значений |

Месячный итог делится на число дней месяца для оценки скорости спроса. Он не распределяется на вымышленные ежедневные продажи. Дневная вариативность в этом режиме неизвестна, поэтому приближение Пуассона и межмесячный разброс явно отмечены в предупреждениях.

Перед оценкой тренда ряд десезонализируется. При наличии таблицы поставщика её коэффициенты нормируются к среднему уровню 1. При отсутствии внешних коэффициентов достаточно длинная история позволяет оценить месячные отношения; короткая история использует нейтральную сезонность. При недостаточном количестве точек наклон равен нулю.

Прогноз вычисляется по дням горизонта: линейно спроецированный уровень ограничивается снизу нулём, умножается на сезонность соответствующего месяца, затем усредняется. `seasonality_factor` и `trend_factor` помогают объяснить результат; их произведение с уровнем не обязано в точности совпадать со средним дневных произведений на границе сезонов.

## 6. Горизонт, потребность и срочность

```text
H = срок нового заказа + период проверки
окно = [as_of, as_of + H)
спрос(H) = средний прогноз в день × H
страховой запас = z(уровень сервиса) × σ × √H
потребность = спрос(H) + страховой запас − остаток − допустимые приходы
заказ = округление вверх max(положительная потребность, MOQ) до кратности
```

MOQ применяется **перед** округлением; MOQ артикула приоритетнее общего условия поставщика. Кратность может быть дробной.

Из потребности вычитаются только приходы с ETA в том же окне. Просроченные, неизвестные, слишком поздние ETA и снимки из будущего относительно исторической даты расчёта не считаются доступным приходом. Их объём показан как `ignored_in_transit`.

Срочность проверяет первый дефицит по последовательности датированных приходов. Наличие большого позднего поступления не скрывает отсутствие товара до его даты. Если суммарного объёма достаточно, но до прихода будет дефицит, строка имеет нулевой дополнительный заказ и рекомендацию ускорить поставку или переместить запас.

## 7. Обоснование и проверки

Каждая строка содержит `Rationale`, предупреждения и текст с фактической единицей товара. Обоснование по умолчанию строится шаблоном; при `explain=true` и ключе используется OpenAI API. LLM не выбирает количество и не заменяет расчёт.

```bash
cd backend
./.venv/bin/python -m unittest discover -s tests -v
RUN_REAL_EXCEL_TESTS=1 ./.venv/bin/python -m unittest tests.test_excel_import -v
./.venv/bin/python -m tests.validate_must_have
```

Последняя команда проверяет пять Must-have-сценариев **на синтетическом наборе**. Регрессии отдельно проверяют даты, склады, ETA, единицы, партии, сверку источников и экспорт. Реальный smoke-тест проверяет чтение приложенных файлов. Текущий результат определяется запуском тестов; это не измерение точности прогноза, достигнутого уровня сервиса или снижения запасов на рабочих данных.
