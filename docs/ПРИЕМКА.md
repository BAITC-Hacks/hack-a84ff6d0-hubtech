# Проверки интегрированного сервиса

Дата: **23.09.2026**. Проверено локальное рабочее дерево после переноса
`baitc/frontend@5a0ace2`, сохранения Excel/EKT и исправления расчёта. Протокол
[qa/results/2026-09-23.json](../qa/results/2026-09-23.json) содержит итоговые числа
и границы проверки. Балльная интерпретация — [отчёт по критериям](ОТЧЁТ_ПО_КРИТЕРИЯМ.md).

## Среда и воспроизводимость

- macOS, **Python 3.12.14**, **Node 24.19.0**, Chromium через Playwright **1.62.1**.
- Создано новое изолированное Python-окружение; установлен `requirements-dev.txt`,
  который подключает закреплённый `requirements.lock`. `pip check` проходит.
- Frontend установлен через `npm ci` и обновлённый lock с Playwright.
  Поддерживаемый контракт Node ограничен `^22.19.0 || ^24.0.0`: прежний минимум
  22.12 не покрывал требования закреплённого jsdom и исправлен. CI использует 22.19.0.
- Использованы настоящее рабочее дерево и приложенные Excel; новый клон на Linux
  не выполнялся. Старое `.venv` с Python 3.9 не использовалось как подтверждение
  совместимости нового сервиса.
- Во всех тестовых сценариях `OPENAI_API_KEY=''`. Расчёт и обоснования проверены
  без внешнего LLM. API/worker/browser запускаются на временных портах со своей БД
  и временными пользователями. Рабочие учётные записи и исходные Excel не меняются.

## Воспроизведение

Сначала установите и настройте среду по [DEPLOY](DEPLOY.md). Ниже команды запускаются
из указанных каталогов; Python `.venv` должен быть **3.12**.

Из `backend/`:

```bash
OPENAI_API_KEY='' RUN_REAL_EXCEL_TESTS=1 .venv/bin/python -m unittest discover -s tests -v
OPENAI_API_KEY='' .venv/bin/python -m tests.validate_must_have
.venv/bin/python -m pip check
```

Из корня репозитория:

```bash
OPENAI_API_KEY='' backend/.venv/bin/python -m unittest discover -s scripts -p 'test_*.py' -v
backend/.venv/bin/python qa/smoke_service.py
backend/.venv/bin/python qa/smoke_service.py --real-data
OPENAI_API_KEY='' backend/.venv/bin/python scripts/backtest_forecast.py
```

Из `frontend/`:

```bash
npm ci
npm test
npm run lint
npm run build
npx playwright install chromium
npm run test:e2e
npm run test:e2e -- --real-data
```

Для другого Python задайте `PYTHON=/absolute/path/to/python`. В CI используется
`PYTHON=python`. Если браузеры установлены в отдельный каталог, одинаковый
`PLAYWRIGHT_BROWSERS_PATH` нужен и установке, и запуску. На Linux системные зависимости
Chromium устанавливаются `npx playwright install --with-deps chromium`.
`QA_OUTPUT_DIR` позволяет сохранить скриншоты, книгу и JSON в выбранном каталоге;
для локальных артефактов подходит игнорируемый `qa/artifacts/`.

## Проверенные эталоны расчёта

| Контрольный пример | Ожидаемый и полученный результат |
|---|---|
| 10 единиц/день, горизонт 7 дней | 70 |
| Месячные продажи ×2 | 70 → 140 |
| Остаток +20 или подтверждённый приход +20 внутри горизонта | 70 → 50 |
| Приход на правой исключённой границе горизонта | Заказ остаётся 70 |
| MOQ 75 / кратность 16 | 75 / 80 соответственно |
| Сезонный коэффициент | 70 → 140 |
| Линейный растущий ряд | 203/день и заказ 1 421 |
| Явный stockout 1–20 мая, месячная история | 40 → 70, историческая добавка 200 |
| Тот же stockout, дневная история | 42 → 70, добавка 200 |
| Один крупный клиент, десять документов | Исключено 200 один раз, заказ 70 |
| Два поставщика | Самостоятельные группы с 70 и 140 и обоснованием |
| Контрольный CSV, сервис 0,5 / период 2 дня | `00123_` → 40 м, uplift 30; `00007` → 10 шт |

Примеры имеют фиксированные даты. Это регрессии алгоритма, а не доказательство
существования stockout/client ID в исходных файлах компании.

## Браузер и экспорт на реальных данных

Через Vite, FastAPI и отдельный worker выполнены:

1. Вход временным менеджером и создание задания на реальных Excel.
2. Открытие сохранённого заказа, изменение первой позиции `130300791_`
   с **6 989 на 6 990 м**, ожидание успешного autosave.
3. Перезагрузка страницы и проверка сохранённого количества.
4. Открытие и закрытие обоснования; проверка формы расчёта при **320 px**.
5. Проверка заказа при **320, 360, 390, 768, 1024 и 1440 px**: нет горизонтального
   переполнения страницы, до 767 px карточки и максимум пять строк поставщика.
6. Ввод `−1`: ошибка в поле и заблокированный экспорт; исправление и сохранение.
7. Подтверждение одной позиции и скачивание XLSX. openpyxl подтвердил **6 990**,
   одну строку и листы «Заказ поставщикам» / «Параметры расчёта».
8. Две реальные вкладки: сервер сохраняет первую правку, вторая получает конфликт;
   явное принятие серверной версии восстанавливает актуальное количество.

Последний прогон занял **31,588 с от нажатия расчёта до завершения проверок**.
Холодная загрузка метаданных, установка и подготовка браузера в это измерение
не входят. Это единичный замер, не нагрузочный профиль или SLA. JavaScript-ошибок
страницы не зарегистрировано. Снимки экрана дополнительно просмотрены вручную.

430 рекомендаций не означают 430 положительных строк заказа: одна позиция
может сообщать о риске опоздавшего прихода с нулевым дополнительным заказом.
Черновик выгружает 429 положительных строк; утверждённый файл контрольного
сценария — одну. Причина отличия сохранена в расчёте, строки не теряются в пагинации.

## Что здесь не подтверждено

- Удалённый запуск нового workflow, новый Linux-клон, применение systemd/nginx
  на целевом сервере и внешний TLS. [`check_linux_deploy.py`](../qa/check_linux_deploy.py)
  включён в Linux CI; на macOS он не засчитан как выполненная проверка.
- Пять ролей, независимое согласование, warehouse/tenant-области, полные бизнес-версии,
  атомарная активация партий, отказоустойчивый кластер и заданные RPO/RTO.
- Правильность неизвестных остатков, интервалов отсутствия, условий поставщиков
  или совместимость импортера конкретной 1С.
- Общая точность модели или экономия. [Backtest](../scripts/BACKTEST.md) показывает
  отсутствие общего преимущества над предыдущим месяцем, а не успешный KPI пилота.
- Safari/iOS/Android на физических устройствах, нагрузочная приёмка, полный аудит
  доступности и безопасность инфраструктуры заказчика.
- Официальный допуск и оценка живого выступления.
