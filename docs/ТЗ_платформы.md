# Техническое задание — сервис автозаказов поставщикам

Формализация кейса ТОО «Электрокомплект». Первоисточник — [../relly-problem.md](../relly-problem.md).

---

## 1. Назначение и цель

Автоматизировать расчёт потребности в пополнении склада: на основе истории продаж, сезонности, устойчивого роста спроса, остатков, товаров в пути, категорий и оценки упущенного спроса формировать **рекомендованные заказы поставщикам**. Цель — снизить издержки на избыточное хранение, сократить дефицит и упущенные продажи, повысить точность регулярных закупочных решений.

---

## 2. Пользователи и роли

- **Менеджер отдела закупа** (основной) — запускает расчёт по складу/категории, получает список рекомендованных заказов с обоснованием, корректирует, утверждает.
- **Администратор** — управляет личными аккаунтами и видит все заказы; дополнительного этапа согласования не вводит.
- **Руководитель закупа** (целевая, Roadmap) — контроль крупных заказов, лимиты.

---

## 3. Функциональные модули

### Модуль 1. Импорт данных 1С
Чтение выгрузок (продажи, месячные продажи/остатки, MOQ, товары в пути, сезонность) с контролем качества и предупреждениями о допущениях.

Дополнительный справочник — локальный JSON из каталога ekt.kz: товарная категория, подкатегория, характеристики и URL. Он не заменяет учётные количества и условия закупки; внутренняя категория 1С сохраняется отдельно. См. [КАТАЛОГ_EKT.md](КАТАЛОГ_EKT.md).

### Модуль 2. Очистка спроса
Выявление крупных заказов по документу или клиенту/дню; в месячном режиме вычитание только после сверки объёмов. Компенсация упущенного спроса реализована для дневной истории с явно переданными интервалами отсутствия.

### Модуль 3. Прогноз спроса
Учёт сезонности и устойчивого роста (не среднее по всей истории).

### Модуль 4. Расчёт потребности
Точка заказа + страховой запас с учётом остатка, товаров в пути, кратности и MOQ.

### Модуль 5. Формирование заказа
Группировка по поставщикам, сортировка по срочности, обоснование по каждой позиции.

### Модуль 6. Экспорт
Выгрузка заказа (черновик / только утверждённые) в Excel по сохранённому расчёту и правкам менеджера. Обработка обратной загрузки в конкретную конфигурацию 1С пока не реализована.

---

## 4. Вход → выход

**Вход:** история продаж (дата, артикул, количество, склад, цена), месячные продажи/остатки, периоды stockout (если есть), справочник поставщиков и сроков, MOQ, товары в пути, материальная ведомость 1С.

**Выход:** список рекомендованных заказов (артикул, поставщик, рекомендуемое количество, обоснование, срочность) в виде таблицы/дашборда с экспортом.

---

## 5. Требования Must-have

| № | Требование | Проверка на синтетике |
|---|---|---|
| 1 | Базовый расчёт потребности по всем источникам | ✅ PASS |
| 2 | Учёт сезонности и устойчивого роста | ✅ PASS |
| 3 | Оценка и компенсация упущенного спроса (stockout) | ✅ PASS |
| 4 | Выявление и исключение разовых крупных заказов | ✅ PASS |
| 5 | Список по поставщикам с обоснованием | ✅ PASS |

Проверка — `backend/tests/validate_must_have.py`, который всегда создаёт синтетический набор. PASS подтверждает эти сценарии, а не полноту реальных данных или точность прогноза на отложенной истории. Клиентов и stockout в реальных файлах нет; месячная ветка stockout не восстанавливает. Опционально: приоритизация по риску дефицита ✅, учёт MOQ/кратности ✅, экспорт ✅; визуализация трендов и авторассылка — Roadmap.

---

## 6. Нефункциональные требования

Приватность (обезличенные данные), объяснимость расчёта, устойчивость к выбросам, совместимость выхода с 1С, воспроизводимость. Детали — в [АРХИТЕКТУРА.md](АРХИТЕКТУРА.md), раздел 10.

---

## 7. Ограничения и допущения

- ❌ Нельзя автоматически отправлять заказ поставщику без подтверждения сотрудника.
- ❌ Нельзя использовать неанонимизированные данные о клиентах.
- Сроки поставки (IEK 21 дн, Systeme Electric 35 дн) — допущения до подтверждения поставщиками.
- Точных интервалов stockout в выгрузках нет; из месячных остатков они не восстанавливаются.
- Полный перечень допущений — в `Dataset.warnings` и [РЕЕСТР_ДАННЫХ.md](РЕЕСТР_ДАННЫХ.md).

## 9. Метрики успеха

- Датированный прогон Must-have на синтетическом наборе — 5/5; после изменения кода требуется повтор.
- Проверяются сценарии влияния поддерживаемых числовых источников на расчёт. Обогащение описаний с сайта влияет на отбор и отображение, а не на числовую потребность отдельного товара.
- Каждая строка заказа сопровождается обоснованием.
- Для целевой эксплуатации: согласованный формат и проверенный импорт в конкретную конфигурацию 1С. Сейчас реализован Excel-экспорт; этот критерий обратной интеграции ещё не проверен.

## 10. Работа без установленной 1С

Прототип запускается на готовых Excel/CSV без клиента 1С. Для регулярной эксплуатации нужны свежие данные; целевой канал чтения согласуется с партнёром: выгрузка по расписанию либо HTTP/OData конкретной конфигурации. Прямой коннектор сейчас не подключён. Контракт и пробелы: [ИНТЕГРАЦИЯ_1С.md](ИНТЕГРАЦИЯ_1С.md).

## 11. Подготовка ML и региональное расширение

Выполнена выборочная интеграция скриптов очистки и подготовки IEK из `baitc/alish` (`5facda2` и предшествующие коммиты скриптов). Доступны локальные признаки, временные разбиения и отчёты качества. Обучение модели, сравнение с текущим прогнозом и измерение точности остаются отдельными работами. Числа подготовки не считаются подтверждением требований к точности: [АУДИТ_ВЕТКИ_ALISH.md](АУДИТ_ВЕТКИ_ALISH.md).

Модель данных допускает несколько складов, но текущие реальные выгрузки подтверждают только Алматы. Восемь дополнительных городов публичного сайта не активированы в расчёте без складской истории, актуальных остатков и приходов. Для приёмки региона нужны сверка источников по складу и проверка отсутствия смешивания регионов: [ГОРОДА_И_СКЛАДЫ.md](ГОРОДА_И_СКЛАДЫ.md).

## 12. Требования внутреннего сервиса

Личные аккаунты manager/admin, сохранённые заказы, решения по строкам отдельно
от неизменяемого расчёта, журнал событий, ревизии и обработка `409` входят в
текущую реализацию. Менеджер работает со своими заказами; администратор — со
всеми. Изменение количества снимает утверждение. Самостоятельной регистрации,
роли руководителя, бюджетных лимитов и автоматической рассылки в этой версии нет.

Длительные расчёты выполняются одним worker через постоянную очередь SQLite;
остальные задания ждут. Есть явная отмена, идемпотентность и лимит выполнения
600 секунд. LLM выключен по умолчанию, общий бюджет объяснений — 120 секунд.
Новый неудачный расчёт не уничтожает прежний сохранённый заказ.

Экспорт `/api/orders/{id}/export` проверяет сессию, владельца/роль и revision,
создаёт лист заказа с 37 столбцами и лист параметров из сохранённой версии.
Обновление источников или справочника EKT не меняет старый расчёт.
`product_category` — отдельный фильтр, не замена `category` 1С; описание сайта
не заменяет числа учётной системы. Старые заказы без описаний EKT читаются.

Эксплуатационная платформа — один Linux-сервер, systemd, nginx с HTTPS,
локальная SQLite WAL, read-only источники и 14 ежедневных копий. Ориентир —
небольшой отдел до 10 одновременных сотрудников; нагрузка и восстановление
подтверждаются на целевом сервере. Приёмка, её исторические результаты и
оставшиеся ограничения — [ПРИЕМКА.md](ПРИЕМКА.md). Таблица PASS выше относится
к указанным синтетическим сценариям, а не подтверждает новый релиз сама по себе.
