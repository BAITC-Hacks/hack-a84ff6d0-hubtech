# Города сайта и склады для расчёта

**Региональное расширение полезно, но город сайта нельзя включать в расчёт без учётных данных его склада.** На предоставленном экране и в публичном разделе контактов EKT перечислены девять городов. В текущих транзакциях проекта подтверждён только Алматы. Производные таблицы ветки `alish` созданы из тех же исходников IEK и не расширяют географию.

Источник перечня: [контакты EKT](https://taldykorgan.ekt.kz/about/contacts/), проверка 23.09.2026 по доступному поисковому представлению страницы и пользовательскому снимку. Это подтверждение списка городов, а не наличия складского API, истории спроса или текущих остатков.

## Почему город не равен складу

Город — географический атрибут, склад — объект учёта. В одном городе может быть несколько складов; центральный склад может обслуживать несколько городов. Город доставки покупателя не обязательно совпадает со складом списания. Названия на сайте не задают устойчивый идентификатор склада 1С.

Нужен отдельный справочник со связью `warehouse_id → warehouse_name → city`. Текущий `Dataset` использует строковое поле `warehouse`; подключение устойчивых идентификаторов и городской группировки необходимо согласовать в адаптере. Городской фильтр не должен суммировать остатки произвольно или скрывать внутренние перемещения. В интерфейсе сейчас сохранён точный смысл «Склад».

## Что уже предусмотрено

Движок считает отдельно по `(sku, warehouse)`. При выборе «Все» данные разных складов остаются раздельными; заказ группируется по поставщику, склад сохраняется в строке и Excel.

`GET /api/meta` формирует список складов из объединения непустых значений `sales`, `monthly_sales`, `stock` и `in_transit`. Исправлено прежнее ограничение списка только транзакционными продажами: склад с месячной историей, запасом или приходом тоже виден. Три проверки закрепляют объединение, исключение пустых/повторных значений и отсутствие выдуманных городов в метаданных. Наличие склада в списке не означает, что для каждого его товара достаточно истории для прогноза.

Публичный каталог EKT остаётся общим справочником описаний товаров. Он не подменяет остатки и сроки складов; `product_category` не является географическим фильтром. Отдельной формы выбора всех девяти городов пока нет.

## Данные для подключения следующего региона

| Набор | Минимально необходимая информация | Для чего |
|---|---|---|
| Склады | Устойчивый код 1С, название, город, активность, роль склада | Сопоставление источников и корректный фильтр |
| Продажи | SKU, склад списания, дата, количество, единица, документ; обезличенный клиент при наличии | Региональный спрос и крупные заказы |
| Месячные отчёты | SKU, склад, месяц, количество и правило пустой ячейки | Согласованная месячная история без смешивания регионов |
| Остатки | SKU, склад, дата/время, физический и свободный остаток, резервы либо согласованная формула доступности | Действительная потребность склада |
| Ожидаемые приходы | SKU, получающий склад, количество, ETA, статус и дата снимка | Покрытие дефицита до поставки |
| Условия поставки | Поставщик, склад/маршрут, подтверждённый срок, MOQ и кратность | Правильный горизонт и партия по региону |
| Межскладские перемещения | Источник, назначение, SKU, количество, статус, ETA | Не считать одно перемещение дважды или продажей клиенту |
| Доступность | Явные интервалы отсутствия либо дневные остатки по SKU/складу | Проверяемая оценка упущенного спроса |

Текущие сроки IEK 21 день и Systeme Electric 35 дней заданы на уровне поставщика и являются допущениями. Их нельзя автоматически считать подтверждёнными для каждого города. Маршрутные сроки и оптимизация перемещений требуют отдельного расширения модели и проверки. Месячная ветка сейчас не восстанавливает stockout даже при появлении интервалов — это также отдельная работа.

## Порядок внедрения

1. Получить у партнёра справочник складов и выгрузки одного следующего региона, сохранив исходные идентификаторы и даты.
2. Сопоставить продажи, месячные отчёты, остатки и приходы; проверить единицы, смысл пустот, области отчётов и отсутствие двойного учёта перемещений.
3. Удалить допущение об Алматы только для таблиц, где появился подтверждённый склад. Не распределять сводный месячный объём по городам без основания.
4. Согласовать сроки поставки для региона и способ адаптации источника к `Dataset`.
5. Проверить фильтр, независимость расчёта складов, сохранение склада в экспорте и поведение при неполной истории. Затем открывать регион для рабочих закупочных решений.

Для прототипа достаточно файлов: устанавливать 1С на машину приложения не требуется. Регулярное получение данных и будущий HTTP/OData-канал описаны в [ИНТЕГРАЦИЯ_1С.md](ИНТЕГРАЦИЯ_1С.md). Качество исследовательского набора и ограничения `alish` — в [АУДИТ_ВЕТКИ_ALISH.md](АУДИТ_ВЕТКИ_ALISH.md).
